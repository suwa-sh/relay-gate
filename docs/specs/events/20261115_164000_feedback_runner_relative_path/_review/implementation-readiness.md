# 実装可能性の判定(2026-11-15 の差分更新)

対象は、今回の差分更新で変えた 6 つの UC と CLI 契約。変えていない UC の判定は前イベントのまま。

| UC | 判定 | 根拠 |
|---|---|---|
| feature flag を設定する | ready | 相対パスの判定・基準・解決後のパス・表示は CLI 契約の runner_path_resolution で 1 つに決まる。正常・実体なし・作業ディレクトリ違い・シンボリックリンク・展開しない場面を BDD で判定できる |
| slot runner の実体スクリプトを割り当てる | ready | 解決後のパスへの問い合わせと警告の表示を BDD で判定できる |
| slot 実行モードを選択して runner を起動する | ready | 起動する実体と、slot runner へ渡す速報クロスチェック runner の値を BDD で判定できる |
| 速報クロスチェック runner へ完了通知を送信する | ready | 受け取る値は解決後の絶対パスで、runner 側の処理は変わらない |
| 元の execution-spec.json から復元して新しい run_id で起動する | ready | 起動する実体と受け渡す値を BDD で判定できる |
| 速報比較依頼を claim する | ready | worker のジョブ定義に書くパスの参照先を足しただけで、処理は変わらない |

## 残っている確認事項

- background 側をリランするコマンドが、起動前に 4 キーの実体をどこまで検査するか。
  - 契約の「読み手ごとの検査の範囲」は検証コマンドと同じ検査と読め、既存の場面は実行権限の無い runner を起動失敗(終了コード 6)として扱う。
  - この読み方の違いは今回より前からあり、今回の変更(相対パスの解決)の結果を左右しない。どちらの場合も解決後のパスを使う。
- 現在の実装は 4 キーの相対パスを拒否する。新しい契約との差分は判断記録 spec-decision-035 に記録した。
