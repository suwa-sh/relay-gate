## 提案 5: 仕様反映後の前提の持ち越しに「文面の再照合」を必須にする

- 対象: tier 実装(前提 AssumptionRecord の再抽出)と、その後の独立した検証
- 事象: 仕様反映後の再走で、契約に明記された項目を explicit として除外する処理は行われたが、残した前提の文面が新しい契約の規則と交差していることを見落とした。前提 A-007(= を含まない行の扱い)の説明文が反映前の「9 キー以外は warn」を言い切っており、実装は契約どおり `FINAL_` を拒否していたのに、検証者は前提と契約の矛盾を blocker と判定した。attempt が 1 つ増え、修正はロジック変更なし(文面・コメント・TDD 追加のみ)だった
- 提案:
  - 前提の再抽出で、変更された契約の節(feedback の反映で差分が出た節)から語彙(規則名・error / warn 文言・キー接頭辞)を取り、持ち越し候補の前提の `assumption` / `reason` 本文を検索する。当たった前提は `carried_forward` にせず `reworded` として文面を新しい規則で書き直し、変更理由に契約の節を記録する
  - 前提の文面が別の規則へ委ねる書き方(「〜と同じ規則に委ねる」)をする場合は、委ねる先の規則を契約の表記で引用することを記載規則にする
  - 検証者側では、contradicts の判定時に「実装は契約に一致し、前提の文面だけが古い」場合を `stale_text` のような区分で記録し、blocker ではなく major(前提の書き直し)として扱う選択肢を検討する(実装が正しいのに attempt が増えるのを避ける)
- 期待効果: 仕様反映後の再走で、前提の文面が原因の attempt 増加を無くす。検証者が実装コメントと前提の両方を古い意図として読む経路を塞ぐ
