# スキル改善提案(既存 SKILL.md は編集しない。提案のみ)

## 提案 1: 実装前に「同一規則の複数表記」を機械的に検出して issue 化する

- 対象: UC 初期化またはテスト足場作成(実装に入る前の段階)
- 事象: feature-flag.env で拒否する確報の制御キーの範囲が、spec.md の処理フロー(`FINAL_*`)、spec.md の分岐条件一覧(`FINAL_CROSSCHECK_MODE` 等)、tier-facade.md(`FINAL_CROSSCHECK_*`)で異なり、CLI 契約は範囲を定めていなかった。実装者は 1 つを選び、独立した検証が境界入力で不整合を検出するまで表面化しなかった
- 提案: spec.md の分岐条件一覧の各行(条件名)をキーに、spec.md のシーケンス図の `alt` 行・tier md の対応節・契約の validation_rules から同じ条件名または同じ error 文言を持つ記述を集め、ワイルドカード(`*`)・接頭辞・列挙のトークンが一致しない場合に `kind: spec_conflict` の issue を自動起票する
- 期待効果: 実装者が表記差を黙って選ぶ経路を塞ぎ、feedback の要求を実装前に起こせる

## 提案 2: AssumptionRecord に「仕様間の表記差から選択した」区分を追加する

- 対象: 実装者の AssumptionRecord 抽出規則と、検証者の verdict
- 事象: 前提の抽出規則は「仕様に無い判断」(spec_absent)を対象にしており、「仕様が複数あって 1 つを選んだ判断」を対象にしていない。今回の選択は前提一覧に載らず、検証者の spec_conformance 観点で初めて major になった
- 提案: AssumptionRecord に `basis: spec_conflict` 相当の区分(または verdict に `spec_conflict`)を追加し、選んだ表記・捨てた表記・根拠 path を必須にする。検証者は同じ区分を blind join で照合し、feedback 作成では `spec_conflict` を仕様起因の要求候補として必ず拾う
- 期待効果: 仕様間の矛盾が S5 の major としてではなく、S4 の記録として一貫して feedback に流れる

## 提案 3: 範囲規則(接頭辞・列挙)には境界ケースの TDD を必須にする

- 対象: tier 実装(TDD)の必須ケース規則
- 事象: BDD Scenario の入力 `FINAL_CROSSCHECK_MODE` はどの解釈でも通過し、表記差をテストが検出しなかった。検証者は `FINAL_RELEASE_LABEL` という境界入力で不整合を検出した
- 提案: 契約の validation_rules に接頭辞・ワイルドカード・列挙が含まれる規則について、「範囲に含まれるが例示に無い値」と「範囲の直外の値」の 2 ケースを TDD の必須ケースとして生成する
- 期待効果: 仕様の表記差と実装の選択が、独立した検証を待たずに実装者側の red で見える

## 提案 4: 仕様反映後の再実行では、契約差分の TDD 化を実装の前に置く(実施済み手順の定型化)

- 対象: 仕様反映後の stale 再実行の手順
- 事象: 今回は、テスト足場の再実行で契約差分(runner_help_probe の 4 項目)を red の TDD として先に追加し、実装の再実行で green にした。前サイクルの major はこの追従で解消した
- 提案: stale 再実行のテスト足場作成で「変更された契約の節を列挙 → 節ごとに TDD ケースを追加 → pass / red を done に記録」を定型手順にし、実装の再実行は red の一覧を入力にする
- 期待効果: 契約差分の追従漏れを検証まで持ち越さない
