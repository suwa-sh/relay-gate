# 提案: 禁止の形の規則の境界と、回答が要る前提の要求化(dist-impl-feedback / dist-impl-verify / dist-spec)

この提案は既存の SKILL.md を変更しない。採否はスキルの保守者が決める。`20261115_093126_proposal-skill.md` の提案に足すもので、置き換えではない。

## 背景

- 「〜を取り込まない」という規則を仕様へ書いた直後の再実行で、同じ規則の一段細かい境界(読み取りの途中の一時的な保持)が新しい前提として出て、要求がもう 1 回必要になった(詳細: `20261115_145719_prohibition-rule-needs-transient-boundary.md`)
- 独立検証が「人の回答が要る」とした前提は、最終確認より前に要求の下書きを作る時点では、まだ人が回答していない。現在の規則(人が仕様の変更として却下した前提だけを要求の候補にする)では、下書きに載せる経路が無い
- 仕様の更新履歴の概要文が追加した BDD を「4 場面」と書き、実際は Scenario 4 本 + Scenario Outline 1 本(実行は 7)だった。本文は正しいが、数の照合に手間がかかった

## 提案内容

| 対象 | 提案 |
|---|---|
| dist-impl-feedback の要求の書き方 | 禁止の形の規則(〜しない)を求める要求には、対象の領域・期間・後に残してよいもの・規則の目的の 4 点を書く、という確認項目を足す |
| dist-impl-feedback の「1. 原因を分類する」 | 独立検証が「人の回答が要る」とした前提(選択肢つきの質問がある前提)は、最初の下書きに、選択肢と推奨を付けた要求の候補として載せてよいと明記する。最終確認で利用者が「実装を変える」を選んだら、その要求を外すか内容を差し替える |
| dist-impl-feedback の as-built summary | 現行の実装を仕様に書く要求では、実装の値の流れ(どこに・いつまで)を手順の表にして、規則の文面と突き合わせる手順を足す |
| dist-impl-verify の前提の判定 | 安全に関わる前提で「定め無し」と判定したときは、質問に「どの領域に・いつまで」を含める(今回の質問はこの形で出ており、要求にそのまま使えた。型として残す) |
| dist-spec の更新履歴の概要文 | BDD の追加数は、Scenario の本数・Scenario Outline の本数・実行数を分けて書く |

## 期待する効果

- 規則を 1 回の要求で決め切り、反映後の再実行でもう 1 回要求を出すことを防ぐ
- 回答が要る前提を、利用者が 1 回の最終確認で決められる
- 仕様の更新と実装側のテストの数を、読み替えなしで照合できる
