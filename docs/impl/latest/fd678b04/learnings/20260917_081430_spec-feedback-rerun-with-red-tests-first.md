# 仕様反映後の再実行は、契約差分を red テストにしてから実装を追従させる

## 何が起きたか

前サイクルの feedback(runner `--help` 問い合わせの契約一元化)が spec に反映され、CLI 契約に `runner_help_probe`(待機上限 4 秒・逐次・TERM → KILL・版 ≠ 1 は未応答・版行の前後空白除去・準備失敗は終了コード 6)が追加された。テスト足場の再実行で、既存実装が契約に未追従の項目(版の値の前後空白除去、版 ≠ 1 の未応答扱い、準備失敗の終了コード 6)を red の TDD ケースとして先に追加し、実装の再実行でそれらを green にした。前サイクルの major(一時ファイル作成失敗が未応答に化ける)はこの追従で解消し、前提だった 3 件(非 0 終了・実体不正時の抑止・待機上限)は契約に明記されたため前提一覧から外れた。

## 原因

- 仕様反映後の再実行では、実装が「前の仕様」に合っている状態から始まる。契約差分を実装で直接追いかけると、追従漏れを検証まで持ち越す
- 反映前に前提(spec_absent)として記録した判断は、反映後に契約の明記と一致するか、契約と食い違うかのどちらかになる。前提一覧をそのまま持ち越すと、明記済みの規則が前提として残り、人の確認対象が膨らむ

## 回避方法

- テスト足場の再実行で、変更された契約の各項目を 1 項目 1 ケースの TDD として追加し、pass / red を記録する(red が実装の追従対象になる)
- 前提の再抽出では、契約に明記された項目を explicit として除外し、除外した旧 ID と根拠(契約の節)を assumptions.yaml のコメントに残す
- 反映された要求の各項目(待機上限・方式・未応答判定・準備失敗)が、契約の節・TDD ケース・前提の除外の 3 つで対応づくことを as-built summary で確認する

## 次回の対応

- 仕様反映後の再実行では、差分の出た契約の節を先に列挙し、節ごとに TDD ケースの有無を確認してから実装に入る
- 前提一覧の差分(除外・追加)を、反映した feedback の要求 ID と対応づけて記録する
