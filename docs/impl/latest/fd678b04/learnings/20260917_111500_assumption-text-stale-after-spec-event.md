# 仕様反映後に持ち越した前提は、文面を新しい契約で読み直さないと実装が正しくても blocker になる

## 何が起きたか

前サイクルの feedback(確報の制御キーの範囲 = `FINAL_` 接頭辞)が CLI 契約 `config_files.feature-flag.env.validation_rules` に反映され、再走の実装(attempt-2)は `FINAL_` 拒否を正しく実装していた。しかし持ち越した前提 A-007(= を含まない行の扱い)の文面は反映前のまま「9 キーなら option required、それ以外は warn: unknown key」と書かれており、独立した検証が等号なしの `FINAL_DB_CONN_REF` 行で実行したところ、実装は契約どおり error で拒否したのに前提の記述は warn を主張していた。検証者はこれを「前提が契約と矛盾」(contradicts)として blocker に判定し、attempt が 1 つ増えた。attempt-3 の修正はロジック変更なしで、前提の文面を契約の優先順(FINAL_ 拒否 → 条件付き option required → 未知キー warn)に書き直し、repository のコメントを同文にそろえ、等号なし `FINAL_` 行の TDD を 2 件追加しただけだった。

## 原因

- 前提の再抽出で「契約に明記された項目を explicit として除外する」ことはしたが、「残す前提の文面が、新しく明記された規則と交差していないか」を読み直さなかった。A-007 は等号なし行という別の論点の前提だが、その説明文の中で未知キーの扱いを反映前の規則で言い切っていた
- 前提の文面は検証者が仕様と照合する対象そのものなので、実装が正しくても文面が古ければ contradicts になる。実装コードのコメントも同じ古い文面だったため、検証者は実装意図まで古いと読めた

## 回避方法

- 仕様反映後の前提の再抽出では、変更された契約の節に出る語(今回は「未知キー」「warn」「FINAL_」)で持ち越し前提の文面を検索し、当たった前提は文面を新しい規則で書き直す(除外判定だけで終わらせない)
- 前提が別の規則へ委ねる部分(「キー名の評価は = のある行と同じ規則に委ねる」)は、その規則の優先順を契約の表記で引用する。自分の言葉で言い切らない
- 前提の文面を変えたら、対応する実装コードのコメントと TDD の説明文も同じ文面にする(検証者はコメントも読む)

## 次回の対応

- 仕様反映後の S4 再走で、assumptions.yaml の各前提について「文面に出る規則名 / 文言が現在の契約と一致するか」を 1 件ずつ確認してから carried_forward にする
- 持ち越し前提の文面を変えた場合は、変更理由(契約の節)を assumptions.yaml のコメントに残す(attempt-3 で実施した形式)
