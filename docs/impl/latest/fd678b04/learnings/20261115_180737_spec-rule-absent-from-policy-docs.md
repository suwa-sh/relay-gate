# 仕様の生成時に足された、方針資料に無い規則に、サンプルを置こうとして初めて気付いた

## 何が起きたか

- feature-flag.env の runner / worker の 4 キーは、仕様では絶対パス必須だった。相対パスは `error: path is not absolute` で拒否していた
- 元の方針資料(しくみ・利用イメージ)の設定例は、2 か所とも 4 キーを `./` で始まる相対パスで書いている。方針資料の設定例は、仕様どおりの検証を通らなかった
- この食い違いは、2026-08-30 の仕様の初回生成から 2026-11-15 まで見つからなかった。設定検証を手元で試すサンプルをリポジトリに置こうとして、置いたままのファイルでは通らないことから初めて気付いた
- 利用者が理由を確認したうえで「相対パスを受け付ける。基準は設定ファイルのあるディレクトリ」と決め、同じ日に仕様と実装を直した。この UC の全工程をもう 1 回やり直した(テストの追加・更新 25 件、実装の関数 3 つ)

## 原因

- 絶対パス必須は、仕様の初回生成時に足された規則だった。要求・方針資料・判断記録のどこにも理由の記載が無かった
- 理由の記録が無い規則は、「方針資料に戻す対象か、意図して足した規則か」を後から区別できない。同じ種類の規則(ジョブマップの作業ディレクトリとスクリプトの絶対パス検査)を 2026-09-22 にやめたときも、4 キーの検査は「変えない」とだけ記録し、理由を書かなかった
- 実装とテストは仕様を正として作るため、仕様が方針資料から離れていても、すべてのテストが通る。BDD の場面も絶対パスの設定だけを使っていた
- 方針資料の設定例を、そのまま入力にして検証を通す確認が、どの段にも無かった

## 回避方法

- 仕様の規則のうち、方針資料に対応する記述が無く、理由の記録も無いものを一覧にする。一覧の各行を「方針資料へ戻す」「理由を記録して残す」のどちらかに振り分ける。実装を始める前に行う
- 方針資料にある設定例・コマンド例は、字面のまま入力にした BDD の場面を 1 つ以上持つ。今回は「方針資料の設定例の書き方(相対パス)の feature flag を検証する」の場面が入った
- 規則を「変えない」と決めたときも、理由を判断記録に書く

## 次回の対応

- 残りの UC を実装する前に、その UC が読む設定ファイルの規則について、上の一覧を作る。対象の例: 比較ツール起動コマンドの絶対パス検査(2026-10 の利用者決定があり、理由の記録がある。残す側)
- 方針資料の設定例を字面のまま使う場面が無い設定ファイルは、場面の追加を仕様への要求に含める
- スキルへの提案は `20261115_180737_proposal-skill.md`、プロジェクトの規約への提案は `20261115_180737_proposal-context.md` に書いた
