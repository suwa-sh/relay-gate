# bash で数 MB の文字列を扱うと遅くなる 4 つの形

## 何が起きたか

- 5,000 行・数 MB の設定ファイルの検証が、制御文字の多い入力で 14〜60 秒以上かかった
- feature flag の検証は attempt 5 で 3〜8 秒まで縮めた(Linux / macOS、ロケール C)
- 同じ形が、速報クロスチェック設定と slot ジョブマップの検証に残っている(本 UC では変更していない)

## 原因

| 形 | なぜ遅いか | 実測の目安 |
|---|---|---|
| 値ごとに bash で文字を置き換える | 制御文字の種類が多い値で、1 バイトあたり数マイクロ秒かかる | 8 MiB で 20 秒超 |
| 1 行ごとに bash のパターン照合で分割・空白除去する | 1 行が数 MB のとき、行の長さの 2 乗に比例する | 8 MiB の 1 行は 60 秒で終わらない |
| 数十 MB の文字列を配列やサブシェルで写す | 可視表記は元の最大 6 倍になる。写すたびに長さに比例する時間がかかる | 1 回 0.1〜0.5 秒 |
| UTF-8 ロケールで長い文字列の長さ・比較を行う | 文字単位の処理になる | ロケール C の 1.3〜2.4 倍 |

値ごとの関数の中で外部コマンドを起動する方法は、5,000 行で 5,000 回の起動になり、かえって遅くなる。

## 回避方法

- 表示する値は、表示の前に一覧でまとめて外部コマンド(sed)へ渡す。値の個数によらず起動は 1〜3 回にする
- 行の構造の取り出し(コメント行の判定、最初の `=` での分割、前後の空白の除去)は sed 1 回で行う。照合は行頭に固定し、行の長さに比例する時間で終わる形にする
- 大きな値を埋め込む行は、組み立てて溜めずに、出すときに直接出す
- 検査の結果をサブシェルで受けない
- 小さな入力(合計 4,096 バイト未満)は bash だけで処理する(外部コマンドの起動のほうが遅い)
- sed は基本正規表現と生のバイトだけで書き、`LC_ALL=C` で実行する(GNU sed と BSD sed の両方で同じ結果になる)
- 外部コマンドを使う箇所には、失敗を終了コード 6 で報告する場所を usecase 側に用意する

## 次回の対応

- 速報クロスチェック設定と slot ジョブマップの検証は、所有する UC の再実行で同じ形に直す。まとめて置き換える関数は共有ファイル `facade/src/domain/cli_field.sh` にあり、そのまま呼べる
- UTF-8 ロケールの差は、検査全体をバイト単位で動かせば縮む見込み(未実測)。利用者が望めば本 UC の中で直す
- 性能の測定は、Linux と macOS、ロケール C と C.UTF-8 の 4 通りで行う
