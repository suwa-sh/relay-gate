# 性能の「目標値」を合否の検査として扱い、作り直しを重ねた

## 何が起きたか

- 独立検証が、制御文字だらけの大きな設定ファイルで 10 秒を超えることを blocker として 3 回続けて指摘した
- 実装は attempt 3 → 4 → 5 と作り直し、やり直し回数の上限を超えて 2 回止まった
- 利用者に確認したところ、「5,000 行・8 MB・10 秒以内」は目標値で、入力の制限でも合否の検査でもなかった(2026-11-13 / 2026-11-15 の決定)
- attempt 5 の残り 2 件(runner の応答待ちとの合算、UTF-8 ロケール)は、目標との差として記録して先へ進んだ

## 原因

- 非機能要求の記載が「10 秒以内に収める」「性能の合否を判定できるようにする」、CLI 契約の記載が「保証する」で、目標値か合否の条件かを読み分けられなかった
- 行の長さは「上限なし」なのに、時間の前提は行数(5,000 行)だけだった。1 行が数 MB の入力で、行数だけでは時間が決まらなかった
- runner の応答待ち(最大 9.2 秒)と検査の時間を足して 10 秒に収める記載(「残り 0.8 秒」)が、小さな設定だけを前提にしていた
- 独立検証は最悪の入力を探すほど指摘を出せるため、合否の線が決まっていないと指摘が終わらない

## 回避方法

- 性能の指摘が blocker で出たら、作り直す前に「その値は目標か、合否の条件か」「大きさの条件は何か」を利用者に 1 回で確認する
- 目標値の場合は、実測を「目標との差」として記録し、止めずに進む
- 性能の回帰テストは、合否の線ではなく「以前より極端に遅くなっていないか」を見る入力に絞る

## 次回の対応

- 仕様へ、目標値であること・大きさの条件・runner の応答待ちの数え方・適用する検証種別を書き足す要求を出した(今回の feedback draft の 1 件目)
- 他の検証種別(速報クロスチェック設定・slot ジョブマップ)の再実行でも、性能は目標との差として扱う
- スキルへの提案は `20261115_093126_proposal-skill.md` に書いた
