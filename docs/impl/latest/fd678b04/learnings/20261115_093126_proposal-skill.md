# 提案: 性能の指摘の扱いと、仕様に定めが無い点の要求化(dist-impl-verify / dist-impl-run / dist-impl-feedback)

この提案は既存の SKILL.md を変更しない。採否はスキルの保守者が決める。

## 背景

- 性能の「目標値」を合否の検査として扱い、作り直しを重ねた(詳細: `20261115_093126_performance-target-treated-as-pass-fail-gate.md`)
- 仕様に定めが無い点を issue に起票していても、利用者が前提を却下しない限り要求の候補にならない。今回は、利用者に選択肢を示して決めてもらうために、オーケストレータの指示で要求の候補にした

## 提案内容

| 対象 | 提案 |
|---|---|
| dist-impl-verify の性能の観点 | 性能の指摘を blocker にする前に、仕様の値が「合否の条件」か「目標値」かを確認する手順を足す。仕様から読み分けられないときは、blocker ではなく「確認が要る指摘」として出し、実測と再現手順を添える |
| dist-impl-verify の findings | 「目標との差」を表す種別を設ける。blocker / major / minor の件数とは別に数え、stage を止めない |
| dist-impl-run のやり直しの判定 | 同じ観点(例: 性能)の blocker が 2 回続いたら、3 回目の作り直しの前に利用者へ「合否の線」を確認する。回数の上限に達してから確認するより早く止まれる |
| dist-impl-feedback の「1. 原因を分類する」 | 仕様に定めが無い前提のうち、issue に起票済みで「利用者が決める」と記録したものは、選択肢と推奨を付けて要求の候補にできると明記する。現在の規則(却下された前提だけを要求にする)では、利用者に選ばせたい点を要求へ載せる経路が無い |
| dist-impl-feedback の draft の書式 | 「変更してほしいこと」に選択肢の表(案・内容・利点・欠点・推奨)を書く形を記述例に足す |

## 期待する効果

- 合否の線が決まっていない観点で、作り直しが続くことを防ぐ
- 仕様に定めが無い点を、利用者が 1 回の最終確認で決められる
