# 異常な入力の守備範囲と拒否時の出力が仕様に定義されていない

- 起票: オーケストレータ(attempt 上限到達時のユーザー判断の記録)
- 種別: 仕様の不足(spec-gap)
- 対象: `validate-config.sh --job-map`(設定ファイルの検証全般に共通する論点)

## 事実

独立検証で、3 回続けて「異常な入力・異常な環境」に関する重大な指摘が出た。

| 回 | 指摘 |
|---|---|
| 1 | fixed_params の JSON 文字列内にある未エスケープ制御文字(TAB / CR / ESC)を受理する |
| 2 | CSV 内の NUL バイトが読み込み時に黙って消え、不正な値を受理する |
| 3 | 値やファイルパスの制御文字がそのまま出力される / 補助コマンドの失敗を検知しない / UTF-8 として不正なバイト列を受理する |

仕様(tier-facade.md の設定契約、cli-command-contract.yaml、ui-design.md の出力フォーマット)には次の定めが無い。

1. 設定ファイルのバイトレベルの異常(NUL、不正な UTF-8、BOM、CRLF)をどこまで検証エラーにするか
2. それらを拒否するときの error 行の文言(現状は最も近い既存の行 `error: csv quote is invalid line=N` を流用している)
3. 任意入力の値・パスを出力するとき、制御文字をどの表記へ置き換えるか(ANSI 禁止と 1 行 1 事実は定めがあるが、置き換え後の表記が無い)

## ユーザー判断(2026-09-19)

- 仕様に無い壊れた入力は、既存のエラー文言で拒否する
- 表示は安全な表記へ置き換える
- 文言の妥当性は仕様への変更要求に含める

## 要求の候補

- 設定ファイル共通の「入力の守備範囲」を設定契約に明記する(拒否する異常の一覧)
- 拒否時の error 行を CLI 契約へ追加する(原因が文言から読み取れるもの)
- 任意入力を表示するときの制御文字の表記規則を出力フォーマット規約へ追加する
- 残りの UC(設定ファイルを読む機能)にも同じ基準が効くよう、cross-cutting に置く
