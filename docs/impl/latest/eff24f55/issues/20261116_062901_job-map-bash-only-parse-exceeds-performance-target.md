## 今回の変更で縮めた差(提案 3 と、提案 4 のうち制約の範囲でできること)

- 表示する値の可視表記を、値ごとに bash で作るのをやめた。報告行をまとめて sed / tr へ渡す(起動の回数は一定。ヘッダーの未知の列名・重複した列名の行も含む)
- 行の長さの 2 乗に比例する処理を除いた
  - CSV の窓ありの状態機械: 8 MiB の行で 60 秒を超えていた。すべての行を窓なしの解析で分けるようにした
  - fixed_params の解析と表記の組み立て: bash の部分文字列の取り出しとパターン置換は、どちらも値全体の長さに比例する時間がかかる。要素の JSON の表記は解析のときに一緒に作る
- 出力のバイト列と終了コードは変えていない
  - 確かめた入力: 既存のテストの入力 122 個、下の表の入力を約 300 KB に縮めたもの 14 個、同梱のサンプル、8 MiB 弱の入力 8 通り
  - 比べ方: 変更前の実装(`git show HEAD:<path>` で取り出した複製)と変更後の実装で、終了コードと stdout・stderr の sha256 を比べた
  - 実行した環境: macOS と Linux。ロケールは `LC_ALL=C`・`LANG=C.UTF-8`・未設定の 3 通り

## 実装で判明した事実

### 実測(`--verbose`。コマンドだけの所要時間。60 秒または 120 秒で打ち切り)

- 測った環境
  - Linux: コンテナ `relay-gate-ci:ubuntu24`(bash 5.2.21、GNU sed、arm64、`LC_ALL=C`、コンテナ内の一時ディレクトリ)
  - macOS: Darwin 25.5.0(bash 5.3、BSD sed、arm64、`LC_ALL=C`)
- 入力は 1 行目のヘッダーと、4,999 行または 1 行のデータ行。大きさは 7.8〜8.2 MB

### 10 秒を超える入力が残る理由

| 入力 | 主な時間 | 理由 |
|---|---|---|
| fixed_params のエスケープが数十万個ある 1 行 | JSON の状態機械 約 80 秒 + CSV の解析 約 7 秒 | セルの `""`(CSV)とエスケープ(JSON)は、1 つごとに bash の処理を数回行う。1 つあたり CSV で約 12 マイクロ秒、JSON で約 35 マイクロ秒。どちらも行の長さに比例する時間で、2 乗の時間ではない |
| 要素が 100 万個を超える fixed_params の 1 行 | CSV の解析 約 34 秒 | 要素ごとに CSV の `""` が 2 つある(約 270 万個) |
| 列が 200 万個を超えるヘッダー | 列ごとの検査(未知の列名・重複の数え上げ)と warn 行 206 万行 | 列ごとに bash の処理を数回行う(1 列あたり約 50 マイクロ秒)。行の長さに比例する時間 |
| macOS の制御文字だらけの job_id(10〜12 秒) | 可視表記を作る sed 約 2.9 秒 + 約 95 MB の文字列を bash で扱う約 2.5 秒 | BSD sed は GNU sed より遅い。可視表記は元の約 6 倍になり、bash が文字列を写すたびに 0.5 秒前後かかる。CSV の解析の制約とは関係がない |

- 引用符とエスケープの対応を決めるには、1 つずつ順に見るしかない
  - `"""abc"` のように、開き引用符と二重化された引用符が並ぶ場合がある
  - bash の一括の置き換えや単語分割では、この区別ができない
- このため、bash だけで解析・検査するという制約のままでは、上の 3 つの形の入力(1 行に数十万〜数百万個)を 10 秒以内にする方法は見つからなかった

## 提案(利用者が決める)

| 選択肢 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A(推奨) | 制約はそのままにする。目標の対象外になる入力の形を仕様に書く。例: 1 つのセルに CSV の `""` または JSON のエスケープが合計 10 万個を超える行、列が 10 万個を超えるヘッダー | 実装と runner の解決関数(同じ関数を共有する)を変えない。実際のジョブマップの fixed_params は数個〜数十個の要素で、この形にならない | 「内容によらず」に例外が入る |
| B | 制約を緩め、セルの解析に awk(POSIX)を使ってよいことにする | 1 行が数十万個のエスケープを含んでも数秒で済む見込み(未実測) | runner の解決関数も変わる。解析を awk と bash で二重に持たないように作り直す必要がある |
| C | 性能目標の「内容によらず」を「通常の内容(制御文字・引用符・エスケープが疎な値)」に緩める | 仕様の変更が小さい | 目標の範囲があいまいになる |

- macOS の 10〜12 秒(制御文字だらけの job_id・引用符の多い script・map_version)は、実行環境(オンプレミスの Linux)では 8〜9 秒(負荷のある回は 10 秒をわずかに超える)
- 推奨: 性能の目標値は Linux での実測で判断する、と仕様に書き添える。開発機の macOS の値は参考にとどめる
