# 仕様還流 2 回目の後の再実行で、変更要求が 0 件に収束した

## 何が起きたか

- 変更要求 2 件(重複 job_id の `lines=` の矛盾 / credential_ref の警告境界)を仕様へ反映した後、tier-facade を attempt 6 で再実行した。
- 独立検証は blocker 0 / major 0 / minor 24 になった。
- issues 6 件はすべて解消済みで、UC BDD 24 Scenario と ATDD 2 Scenario も pass した。
- 仕様起因の未解決の要求は 0 件になり、変更要求の draft を作らなかった。

## 原因

- 前回の要求が「推奨案」と「利用者が選んだ案」を明記していたため、還流の結果が実装とそのまま一致した。
  - 重複 job_id: 推奨案(初出行を含む)が BDD と現行実装に一致していた。
  - credential_ref: 利用者が承認時に案 A(warn で受理)を選び、還流でその選択が仕様に書かれた。
- 仕様に明記された判断は前提ではなくなり、前提一覧から消えた(A-012)。

## 回避方法

- 還流後の feedback では、issue ごとに「仕様のどこに反映されたか」を仕様の path と節名で確認する。
- 確認結果を issue 単位の解消判定表に残す。
- 前提の一覧は前回と差分を取り、消えた前提が仕様に明記されたことを確かめる。
- `review-notes.md` の `spec_change` の却下が 0 件なら、spec_absent の minor 前提は要求にしない。

## 次回の対応

- 変更要求には、実装への影響が無い推奨案と、承認時の利用者の選択を明記する。
  - 還流後の再実装が「文言の追従」だけで済み、還流の回数が減る。
- confidence が low で、仕様の文言と解釈が分かれる前提(今回は A-016)は、as-built summary の「レビューで確認してほしい前提」に挙げる。
  - 人が `spec_change` で却下したときだけ、次の refresh で要求にする。
