# 守備範囲が仕様に無いと、バイトレベル入力の独立検証が収束しない

## 何が起きたか

- `validate-config.sh --job-map`(設定ファイルの CSV を検証する CLI)で、独立検証が 4 回続けて新しい blocker を出した。
- 4 回とも「異常な入力・異常な環境」の堅牢性の指摘だった。

| attempt | 新しい blocker |
|---|---|
| 1 | JSON 文字列内の未エスケープ制御文字を受理 |
| 2 | NUL バイトが `read` で消え、不正な値を受理 |
| 3 | 制御文字をそのまま出力 / 補助コマンドの失敗を見逃す / 不正 UTF-8 を受理 |
| 4 | 事前点検と読み込みの間のファイル差し替えで不正な行を受理 |

- 前提(AssumptionRecord)は 23 → 17 → 28 → 34 件と増えた。
- bats は 143 → 168 → 219 → 277 件と増えた。
- attempt 上限 3 を超え、利用者の判断で 4 回目を実施した。4 回目でも同種の指摘が出たため、仕様の確認待ちに切り替えた。

## 原因

- 仕様は「文字コード UTF-8」「改行 LF」を定めるが、違反時の扱いを定めていなかった。
- 検証中の差し替えや補助コマンドの故障など、異常環境をどこまで守るかも定めていなかった。
- 独立検証は、異常系を 1 つ見つけるたびに blocker と判定できた。守る範囲に上限が無いため、指摘が尽きなかった。
- 実装側は、指摘を直すたびに新しい仕組み(事前走査、補助コマンド、出力の検査)を足した。その仕組み自体が、次の攻撃面になった(例: 事前走査の追加が、4 回目の差し替え競合を生んだ)。

## 回避方法

- 設定ファイルを読む UC は、実装前に「入力の守備範囲」を決める。
  - バイト(NUL、不正 UTF-8、BOM、CR)、行(最終行の改行、空白行、長さ)、構造(重複ヘッダー)、環境(検証中の差し替え、補助コマンドの失敗)ごとに、拒否 / 警告 / 受理 / 対象外を決める。
- 検証の入力は、最初に 1 回だけ読み、以降のすべての検査で同じ内容を参照する(単一のスナップショット)。
- 守備範囲の外の指摘は、blocker ではなく変更要求の候補として扱う。

## 次回の対応

- 残りの UC(クロスチェックのジョブマップ、対象カタログなど)の S1 で、守備範囲が仕様にあるかを確認する。
- 無ければ、実装に入る前に変更要求を出すか、利用者に守備範囲を決めてもらう。
- 同種の blocker が 2 回続いた時点で、attempt の上限を待たずに守備範囲の未定義を疑う。
