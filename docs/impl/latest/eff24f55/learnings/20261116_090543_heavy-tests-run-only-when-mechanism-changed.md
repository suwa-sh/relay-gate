# 時間を確かめるテストが開発機の負荷で毎回違うものが時間切れになった。重いテストは印で分け、仕組みを変えたときだけ流す運用にした

## 何が起きたか

- 2026-11-16 の再実行(`--job-map` の性能改善)で、tier-facade の bats の全件(579 件)を何度も流した。
- 開発機は、別セッションのテストと並走して load average が 18〜45(多くの回で 40 前後)だった。
- 時間を確かめる既存のテストが、流すたびに違う 1 件だけ時間切れ(10 秒)になった。どちらも今回変更していない共有関数のテストで、単独で流し直すと通った。

| 環境 | 時間切れになったテスト | 全件の中 | 単独で再実行 |
|---|---|---|---|
| macOS | `test/domain/cli_field_batch.bats`(5,000 個・8 MB の制御文字だらけの値を 10 秒以内に可視表記にする) | 11.6 秒 | 7.5 秒 |
| Linux コンテナ | `test/domain/cli_field_escape_paths.bats`(制御文字が半分を占める 100 万バイトの値を 10 秒以内に置き換える) | 10.8 秒 | 5.7 秒 |

- 1 件 2 秒以上かかるテストは macOS で 32 件・Linux で 37 件あり、最大は 1 件で 72.7 秒(macOS)・58.0 秒(Linux)だった。全件を流す 1 回が長く、開発中の確認の回数を減らしていた。

## 原因

- 時間を確かめるテストは、実装の速さではなく、その時の機械の空き具合で結果が変わる。負荷が高い開発機では、どれが時間切れになるかが毎回変わる。
- 長時間・大容量のテストを、変更と関係なく毎回すべて流していた。変更していない共有関数の時間のテストが、今回の変更の合否を左右していた。
- 仕様は性能を「目標値であり合否の検査ではない」と定めている(`cli-command-contract.yaml` の `config_input_rules.performance_target`)。時間のテストを毎回の合否に入れると、この位置付けとも合わない。

## 回避方法

利用者の指示(2026-11-16)で、次の運用にした(commit 9ce28e6)。

| 項目 | 内容 | 場所 |
|---|---|---|
| 印 | 1 件で 2 秒以上かかるテスト・MB 級の入力を作るテストの `@test` の直前に `# bats test_tags=heavy` を付ける | 各 bats ファイル |
| 通常のテスト | `bats -r --filter-tags '!heavy' test`(重いテストを除く) | `docs/impl/latest/impl-config.yaml` の `commands.test`、CLAUDE.md、CI |
| 重いテストを流すとき | 対象の仕組みのソースか重いテスト自身が変わったときだけ、`node scripts/ci/heavy-test-files.js <tier_dir> <base_ref>` が出したファイルを `bats --filter-tags heavy <files>` で流す | `scripts/ci/heavy-test-files.js`、`.github/workflows/ci.yml` |
| 対応表 | 重いテストのファイルと、それが確かめる仕組みのソースの対応 | `scripts/ci/heavy-tests.json` |
| ずれの検出 | 印のあるファイルと対応表の一致を `node scripts/ci/heavy-test-files.js --check` で検査する(CI で常時実行) | CI |

- 独立した検証は、通常のテスト 537 件を macOS と Linux で、重いテスト 42 件を Linux で 1 回だけ流し、すべて通った。選択スクリプトが、無関係な変更では 0 ファイル、共有の repository の変更では関連する 10 ファイル、対応表の変更では全 14 ファイルを選ぶことも確かめた。
- 時間切れが出たときは、そのテストだけを単独で流し直し、変更した仕組みのテストかどうかを記録に残した(S4 done の `gate_runs[].flaky`)。

## 次回の対応

- 重いテストを足したら、同じ変更で `scripts/ci/heavy-tests.json` に足す。CI の `--check` が落ちたら対応表を直す。
- 時間を確かめるテストは「この入力なら、この時間以内に終わる」の確認として置き、性能の目標の合否にしない。重いテストとして印を付ける。
- 性能の比較は、負荷の小さい回に、実行環境と同じ Linux コンテナで測る。負荷のある回の値はばらつき(1〜2 秒、macOS では最大 2 倍)として扱い、目標との差の根拠にしない。
- 他の tier(rapid-crosscheck / final-crosscheck / ops)で時間のかかるテストを書くときも、最初から印を付けて対応表に足す。
