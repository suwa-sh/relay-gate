# スキル改善の提案(dist-impl-implement / dist-impl-verify / dist-impl-run)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。

## 提案 1: 実行環境(Linux)相当での検証を S4 ゲートまたは S6 / S7 の記録に含める

- 現状: S4 のゲート(format / lint / tdd / bdd_tier)は開発機で実行される。実行環境が Linux でも、開発機が macOS なら macOS の結果だけで S9 の承認に進む。
- 問題: macOS で green の実装が Linux CI で 5 件失敗した(UTF-8 ロケールの `read` / SIGPIPE 無視 / 性能差)。承認後に差し戻しになり、attempt 内で S4〜S7 を 2 回再実行した。
- 提案:
  - `impl-config.yaml` に任意の `runtime_equivalent_check`(コンテナイメージと実行コマンド)を定義できるようにする。
  - 定義があれば、S4 の tdd ゲートの後(または S6 / S7 の done)で実行し、結果を `linux_equivalent_check` のような固定フィールドで記録する。
  - 未定義のときは現状どおり(開発機のみ)。

## 提案 2: Verifier にロケール 3 通りの CLI 実行を標準観点として入れる

- 現状: 今回の独立検証は `LANG` 未設定 / `LANG=C.UTF-8` / `LC_ALL=C` で stdout・stderr・終了コードのバイト一致を独自に確かめ、blocker F-001 を見つけた。
- 問題: この観点は検証者の裁量で、他の UC や tier で再現される保証が無い。
- 提案: `dist-impl-verify` の `operability` または `spec_conformance` の観点に「CLI 出力がロケールに依存しないこと(3 通りで一致)」を bash / CLI tier の標準項目として明記する。

## 提案 3: AssumptionRecord の除外規定(内部の実装選択)を明文化する

- 現状: 検証者は V-001〜V-005(CSV の高速経路 / 1024 バイト窓 / fixed_params の早期判定と再利用 / `LC_ALL=C` の重複設定の省略)を「仕様に無い性能上の設計判断」として unlisted と判定した。実装者は「外から観測できる挙動を変えない内部の実装選択」として記録しなかった。
- 問題: `assumption-record.md` の `performance` カテゴリは記録対象を定めるが、観測可能な挙動を変えない内部選択を除外してよいかの規定が無い。実装者と検証者の解釈が分かれ、minor 5 件が 2 サイクル続けて残った。
- 提案: `assumption-record.md` に次のどちらかを明記する。
  - 案 A: 観測可能な挙動(出力・終了コード・永続化・外部 I/O)を変えない内部選択は記録しない(除外条件に追加)。
  - 案 B: `performance` カテゴリは観測可能な挙動を変えなくても記録する(今回の検証者の解釈)。
  - 推奨は案 A。レビューで人が判断する価値があるのは観測可能な前提だけであり、内部選択は Verifier の `refactoring` 観点で読めばよい。
