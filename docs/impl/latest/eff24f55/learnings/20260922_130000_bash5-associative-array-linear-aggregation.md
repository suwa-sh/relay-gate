# bash 5.0 を前提にできたので、連想配列で版の集計を行数に比例させた(5,000 行で 36 秒 → 4 秒)

## 何が起きたか

- 前回のサイクルでは、対象の bash の版が仕様に無く、実装は版に依存しない構文(連想配列を使わない)を選んだ。
- map_version の distinct 値の集計は、配列の全要素との比較(行数の 2 乗)で書かれていた。
- 仕様還流で、想定最大行数 5,000 行(NFR B.1.1.2)と、最悪条件(全列に値、job_id 全行一意、map_version 全行相違)が確定した。

| 行数 | 改善前(2026-09-21 の実測) | 改善後(attempt 6、独立検証の実測) |
|---|---|---|
| 1,000 | 2.2 秒 | - |
| 3,000 | 13.8 秒 | - |
| 5,000 | 36 秒 | 3.9 秒(`--verbose` 4.8 秒) |

- 目標は CLI 応答 10 秒以内(NFR B.2.1.1)。改善前は 5,000 行の最悪条件で超えていた。

## 原因

- 版の集計が「見たことがある値か」を配列の線形探索で判定していたため、distinct 値が行数に比例して増える最悪条件で 2 乗の時間になった。
- 連想配列(bash 4.0 以上)を使えば 1 回の参照で判定できるが、bash の最低版が仕様に無かったため避けていた。

## 回避方法

- 仕様還流で CLI 契約 `runtime_prerequisites.bash_minimum_version: "5.0"` が確定した。連想配列・`mapfile`・`${var@Q}` を前提にしてよい。
- 版の集計は連想配列で「初出かどうか」を判定し、初出順の配列に追加する(初出順の並びは前提 A-017)。
- 残りのコストは CSV 行の解析(約 0.23 ms/行)と行ごとの検証・解決結果の組み立て。fixed_params の典型形(エスケープ・空白なし)の早期解析、JSON 組み立ての早期判定、解析結果の再利用、セルの直接 bind で削った。
- 性能の判定は、NFR の最悪条件(全列に値、キー列全行一意、版の列全行相違)で 5,000 行を実測する。典型の内容(map_version 全行同一)だけで測ると 2 乗の経路が見えない。

## 次回の対応

- 設定ファイルを読む他の機能(クロスチェックのジョブマップ、対象カタログ)でも、「重複検査」「distinct 集計」は連想配列で行数に比例させる。
- 実装の完了条件に、NFR の最悪条件での 5,000 行の実測(10 秒以内)を含める。実測は macOS / bash 5.3 のため、Linux / bash 5.0 での確認は CI または実行環境で別途行う。
