# スキル改善の提案(dist-impl-feedback)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。

## 提案 1: 要求 0 件のときの解消判定を done に構造化して残す

- 現状: 要求が 0 件のとき、done は `draft_path: null` と件数だけを持つ。
- 問題: 還流後の再実行で 0 件になったとき、各 issue と finding をどう判定したかが done から読めない。
- 提案: done に次の任意フィールドを定義する。
  - `resolution.issues[]`: issue の path、判定(`resolved` / `not_spec_issue` / `open`)、仕様側の根拠 path
  - `resolution.findings`: blocker / major / minor の件数、spec_absent の件数、`spec_change` の却下件数
  - `resolution.previous_feedback_ids[]`: 反映済みと判定した過去の feedback ID

## 提案 2: 前提の解釈が分かれる箇所をレビューへ渡す欄

- 現状: spec_absent の前提は、人が `spec_change` で却下しない限り要求にならない。
- 問題: confidence が low で、仕様の文言そのものと解釈が分かれる前提(例: 仕様は「推奨値との差は info」と書き、実装は専用行を出さない)は、一括承認に埋もれやすい。
- 提案: as-built summary に「レビューで確認してほしい前提」の節を標準で設ける。
  - 対象: confidence が low、かつ仕様に関連する記述があるのに具体形が無い前提
  - review 資料の生成側がこの節を個別確認の候補として拾えるようにする。
