## 提案 5: refresh で「要求の前提になった欠陥」が解消したときの重大度の見直し規則

- 対象: dist-impl-feedback の refresh
- 事実:
  - 変更要求 CR-eff24f55-001 は、未解決の blocker(attempt 4 の F-001)を背景に blocker とした。
  - review の差し戻しで F-001 を修正し、attempt 5 で解消した。
  - refresh の手順には、要求の背景になった欠陥が解消したときに重大度をどう見直すかの規則が無い。
- 提案:
  - refresh で、各要求の重大度の根拠(未解決の欠陥 / 検証が収束しない / 他の機能を止める)を記録する。
  - 根拠の欠陥が解消したら、残る根拠で重大度を再判定し、判定理由を done に書く。
  - 重大度を下げると承認証跡の blocker 件数が変わるため、review で再確認が必要かを明示する。

## 提案 6: review 後に追加された前提の扱い

- 対象: dist-impl-feedback の refresh、dist-impl-review
- 事実:
  - attempt 5 で、前提 A-045〜A-048 が review の後に追加された。
  - review の「回答任意の前提は一括承認」は、review 時点の前提だけを対象にしている。
  - A-047(一時ファイルの置き場所・権限、security、major)には、独立検証の確認質問が付いた。
- 提案:
  - refresh で、review 後に追加された前提を、既存の一括承認と区別して一覧にする。
  - 既存の要求の根拠に吸収できる前提は、要求を増やさず根拠へ追記する。
  - security の前提は、再生成する review で人の確認対象として提示する。
