# 出力を変えない性能改善は、変更前の実装を取り出して同じ入力で出力のハッシュを比べる差分テストで確かめた

## 何が起きたか

- 2026-11-16 の再実行では、機能の直しは無く、`validate-config.sh --job-map` の所要時間だけを縮めた。終了コード・stdout・stderr のバイト列は変えない約束だった。
- 変更は解析の中心(CSV の分解・fixed_params の JSON の状態機械・報告行の可視表記)に及んだ。既存の bats と BDD は、出力の一部(含まれる・行数)しか確かめないものが多く、それだけでは「バイト列が同じ」を言えなかった。
- 実装者と独立した検証の両方が、変更前と変更後の実装を同じ入力で実行して比べる差分テストを行い、差は 0 件だった。

| 誰が | 入力 | 条件 | 比べたもの | 件数 | 差 |
|---|---|---|---|---|---|
| 実装者 | 既存テストの入力(記録用の差し替えで集めた)124 個・同梱のサンプル・既知の差の形を約 300 KB に縮めたもの 14 個 | macOS と Linux、ロケール 3 通り(`LC_ALL=C` / `LANG=C.UTF-8` / 未設定) | 終了コードと stdout・stderr の sha256 | 139 入力 | 0 |
| 実装者 | 8 MiB 弱の既知の差の入力 | 8 通り | 同上(Linux は stdout にコンテナ内の一時パスが入るため stderr と終了コード) | 8 | 0 |
| 独立した検証 | 112 入力 × `--verbose` の有無 × ロケール 4 通り | macOS と Linux の各 896 比較 | 終了コードと stdout・stderr の生バイト | 896 × 2 | 0 |
| 独立した検証 | 解析関数への入力(CSV 1,097 件・JSON 2,000 件。固定の乱数の種) | 両 OS | 戻り値と解析後の配列のバイト列 | 3,097 | 0 |
| 独立した検証 | 改行・タブ・ESC・C1・日本語・コマンド置換を含むパス | 両 OS | 同上 | 48 | 0 |

## 原因

- 出力のバイト列を全部確かめるテストは、入力の形(制御文字・引用符・エスケープ・ヘッダーの異常・大量の診断)の組み合わせが多く、期待値を手で書くと漏れる。
- 性能改善は「同じ結果を速く出す」変更なので、正解は変更前の実装そのものである。変更前の実装を基準にすれば、期待値を書かずに全組み合わせを比べられる。

## 回避方法

- 変更前の実装は `git show HEAD:<path>` で一時ディレクトリへ取り出した。作業ツリーを書き換える `git stash` は使わない(並走するテストや検証を壊さない)。
- 同じ入力ファイル・同じパス・同じ引数・同じ環境変数で両方を実行する。パスは出力に入るため、入力のパスをそろえる。
- 比べるのは、終了コード・stdout・stderr の sha256(または生バイト)。行数や「含まれる」ではなく全バイトを比べる。
- ロケールは 3〜4 通り(`LC_ALL=C` / `LANG=C.UTF-8` / 未設定 / 導入されていれば `ja_JP.UTF-8`)、OS は開発機と実行環境(Linux コンテナ)の両方で比べる。
- 入力は、既存テストの入力を記録用の差し替えで集めたものに、変更した処理を狙う形(長い行・多数の `""`・多数のエスケープ・大量の診断)を足す。解析関数は CLI とは別に、乱数で作った入力でも比べる。
- 補助コマンド(sed / tr / sort / cat / rm)の失敗を差し込んだ回も、終了コードと出力の抑止が変わらないことを確かめた(SIGPIPE を通常の扱い・無視の両方)。

## 次回の対応

- 出力を変えない性能改善・リファクタリングでは、この差分テストを完了の条件にし、件数と差の数を S4 done(`output_equivalence`)と S5 findings(`verification_evidence`)に残す。
- 差分テストのスクリプトと入力はリポジトリに残さず一時ディレクトリに置く(今回の実装者・検証者とも同じ)。手順を開発規約に書く提案は `learnings/20261116_090543_proposal-context.md` の提案 2 に書いた。
- 他の検証種別(`--rapid-crosscheck` など)の性能改善でも、同じ手順で確かめる。
