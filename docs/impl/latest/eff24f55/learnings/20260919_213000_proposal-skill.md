## 提案 1: S1 で「入力の守備範囲」の有無を確認する

- 対象: dist-impl-run の S1(uc-init)の input-preflight
- 事実: 設定ファイルを読む UC で、独立検証が 4 回続けて異常入力・異常環境の新しい blocker を出した。守る範囲が仕様に無かった。
- 提案:
  - UC がファイルや外部入力を読む場合、仕様に守備範囲(バイト異常・行異常・構造異常・異常環境ごとの扱い)があるかを確認する。
  - 無ければ、実装前に利用者へ「守備範囲を先に決めるか」を確認する。
  - 決めない場合は、S4 の dispatch 指示に「守備範囲外の異常は既存の文言で拒否する」などの暫定方針を明記する。

## 提案 2: 同種の blocker が続いたら上限前に止める

- 対象: dist-impl-run の attempt 制御
- 事実: attempt 1〜4 の blocker は、すべて同じ種類(異常入力・異常環境の堅牢性)だった。上限 3 まで自動で回り、その後に利用者が 1 回延長した。
- 提案:
  - S5 の blocker に、種類(例: 仕様との矛盾 / 仕様の範囲外の堅牢性)を付ける。
  - 「仕様の範囲外の堅牢性」の blocker が 2 回続いたら、上限を待たずに利用者へ仕様ブロックの経路を提示する。

## 提案 3: Verifier が守備範囲外の指摘を blocker にしない基準

- 対象: dist-impl-verify の severity 判定
- 事実: 4 回目の blocker は、補助コマンドの関数差し替えで差し替えのタイミングを制御して立証した。通常の運用では起きない。
- 提案:
  - 仕様に守備範囲がある場合、範囲外の指摘は minor か変更要求の候補にする。
  - 仕様に守備範囲が無い場合、指摘に「守備範囲の未定義」を明記し、feedback の候補として扱えるようにする。
