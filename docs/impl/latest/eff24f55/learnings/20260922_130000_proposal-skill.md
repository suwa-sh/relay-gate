# skill への改善提案(eff24f55 仕様還流後のサイクル由来)

既存の SKILL.md は変更していない。採否は人が判断する。
前回の提案(`20260919_213000_proposal-skill.md`)の 4 件は維持する。本ファイルは今回のサイクルで新たに見えたものだけを書く。

## 提案 1: Verifier 指示にハッシュの算出コマンドを明記する

- 対象: dist-impl-verify(findings の `assumptions_sha256` の記録)と、dist-impl-run の S5 dispatch 指示
- 事実: 2 attempt 続けて、Verifier が記録した `assumptions_sha256` の算出基準(生バイト / canonical record)が期待値と食い違い、内容を変えない差し戻しが起きた。attempt 6 では Verifier が「利用者の指示が canonical hash より優先する」と解釈し、意図的に生バイトの値を記録した。
- 提案:
  - S5 の dispatch 指示のテンプレートに、`node validateAssumptions.js record <path>` の出力を転記する旨と、そのコマンドを 1 行で書く。
  - dist-impl-verify の完了条件に「findings に書く前に同じコマンドで再計算し一致を確認する」を加える。
  - オーケストレータは、形式だけの差し戻しをしたら次の attempt の指示にも同じ算出コマンドを繰り返す(Verifier は attempt をまたいで記憶しない)。

## 提案 2: 人が承認した前提を、次の attempt の Verifier に引き継ぐ

- 対象: dist-impl-run の S5 dispatch(前提の引き継ぎ)、dist-impl-verify の severity 判定
- 事実: 前提 A-012(credential_ref の形式不一致は warn で受理)は 2026-09-19 のレビューで利用者が承認した。仕様は変わっていないため、attempt 5 再実行と attempt 6 の Verifier は同じ前提を再び major として確認要求した。
- 提案:
  - 承認 event の `assumption_decisions` を、次の attempt の Verifier 指示に「人が確認済みの前提(id と決定)」として渡す。
  - Verifier は、確認済みの前提が同じ内容(id・assumption 本文が一致)なら verdict を記録しつつ severity を minor に下げ、`kind: human_confirmed` で区別する。仕様が変わって前提の根拠が消えた場合だけ元の severity に戻す。
  - 承認が仕様の確定を意味しないことは変えない(仕様の未指定は変更要求で解消する)。

## 提案 3: 仕様の中の矛盾を、S1 の入力点検で機械的に検出する

- 対象: dist-impl-run の S1(uc-init)の input-preflight、または dist-spec の生成時の整合チェック
- 事実: CLI 契約と tier 仕様の列検証表は「2 回目以降の行番号」、同じ tier 仕様と UC 仕様の BDD は「初出行を含む `lines=2,5`」で、仕様の中で矛盾していた。実装と独立検証が 2 attempt かけて見つけた。
- 提案:
  - BDD の Then に現れる固定文字列(`error: ... lines=2,5` など)を、CLI 契約の stderr 定義の書式(`lines=<n1,n2,...>` とその注記)と突き合わせる点検を S1 に加える。完全な検証は難しいが、「注記が Given の入力と矛盾する例」は Given の行番号と Then の列挙を比較すれば機械的に検出できる。
  - 検出したら、S4 に入る前に変更要求の候補として利用者へ提示する(実装者が本文と BDD のどちらを優先するかを決めない)。

## 提案 4: 「仮採用」注記のある仕様は、実装前に確定を促す

- 対象: dist-impl-run の S1、dist-spec
- 事実: UC 仕様の業務ルールに「(拒否はしない。仮採用)」の注記が残っており、Verifier はこの扱いを毎回確認対象にした。`docs/todo.md` の低確信度の仮採用値と同じ性質である。
- 提案:
  - S1 の input-preflight で、対象 UC の spec.md / tier-*.md に「仮採用」の語があれば一覧化し、利用者に「実装前に確定するか、実装後の変更要求に回すか」を 1 問で確認する。
  - dist-spec は、仮採用の注記を `docs/todo.md` のエントリと相互参照させ、確定時に両方が消えるようにする。
