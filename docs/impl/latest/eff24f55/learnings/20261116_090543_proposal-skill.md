# スキル改善の提案(dist-impl-implement / dist-impl-verify / dist-impl-feedback)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。

## 提案 1: 出力を変えない変更(性能改善・リファクタリング)の標準の確かめ方として、差分テストを dist-impl-implement と dist-impl-verify に入れる

- 現状: 2026-11-16 の再実行は、出力を変えない性能改善だけだった。実装者と検証者は、それぞれ独自の判断で、変更前の実装を取り出して同じ入力で出力を比べた(実装者 139 入力、検証者 896 比較 × 2 OS、差 0)。スキルにはこの手順が無い。
- 問題: 検証者の裁量に任せると、他の UC では「既存テストが通った」だけで「出力は変えていない」とされるおそれがある。既存テストは出力の一部しか確かめないことが多い。
- 提案:
  - dist-impl-implement の tier-impl: S4 done に任意の `output_equivalence` 節(比べ方・入力の数・条件・差の数)を定義する。dispatch で「出力を変えない」と指定された回は必須にする。
  - dist-impl-verify: 同じ指定の回は、`refactoring` 観点の標準項目に「変更前の実装との差分実行(終了コード・stdout・stderr のバイト比較)」を入れる。
  - 手順の詳細は `learnings/20261116_090543_output-preserving-perf-change-differential-test.md` の「回避方法」。

## 提案 2: 時間を確かめるテストと重いテストの扱いをスキルの既定に入れる

- 現状: dist-impl-implement の tdd ゲートは `commands.test` を全件流す。重いテストを分ける仕組みはプロジェクト側(relay-gate)で作った(`# bats test_tags=heavy`、`scripts/ci/heavy-test-files.js`)。
- 問題: 負荷の高い開発機では、時間を確かめるテストが流すたびに違う 1 件だけ時間切れになり、変更と無関係な不合格が出た(`learnings/20261116_090543_heavy-tests-run-only-when-mechanism-changed.md`)。
- 提案:
  - `impl-config.yaml` に任意の `commands.test_heavy`(重いテストを選んで流すコマンド)を定義できるようにし、S4 の最終ゲートでだけ流す。
  - S4 done の `gate_runs` に、時間切れを単独の再実行で確かめた記録の固定フィールド(例: `flaky[]` の test・全件の中の時間・単独の時間・変更した仕組みかどうか)を定義する。今回は自由記述で残した。

## 提案 3: 観測できる挙動を変えない内部の選択の記録の規則を決める(再発)

- 現状: 今回も、実装者が記録しなかった内部の選択(検証全体を C ロケールで行う)を、検証者が「前提一覧に無い」と判定した。出力のバイト列は 4 通りのロケールで変わらない。
- 経緯: 2026-10-06 の提案(`learnings/20261006_080400_proposal-skill.md` の提案 3。AssumptionRecord の除外条件を明文化する)と同じ種類で、まだ取り込まれていない。今回の実装者は性能の内部の選択 4 件を記録したが(前回の検証者の解釈に合わせた)、C ロケールの選択だけが漏れた。
- 提案: 2026-10-06 の提案 3 のどちらかの案を取り込む。案 B(性能の内部の選択も記録する)を採るなら、dist-impl-implement の前提の洗い出しの手順に「実行時の環境(ロケール・umask・IFS 等)を関数の中で変えた箇所」を候補として挙げる項目を足す。

## 提案 4: dist-impl-feedback の mode の名前をそろえる

- 現状: dist-impl-feedback の SKILL.md の mode は `initial` / `refresh` / `publish`。今回のオーケストレータの指示は `mode=draft` と書いた(dist-impl-run の SKILL.md には `mode=draft` の記載は無い)。
- 問題: 指示を受けた側は、`draft` を `initial` と `refresh` のどちらとして実行するかを、未公開の draft の有無から推測する(今回は draft が無いため `initial` として実行した)。
- 提案: dist-impl-feedback の SKILL.md に「`draft` は、未公開の draft が無ければ `initial`、あれば `refresh` として扱う」と書くか、dist-impl-run の S8 の dispatch の例に `mode=initial` / `mode=refresh` を明記する。
