# スキルへの提案(distillery-impl)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。

## 提案 1: issue の「仕様へ要求を出す」提案に、出さない場合の実害を書かせる

- 現状: テストの骨組みと実装の段階で起票する issue は、「提案」の節に「仕様の変更要求を出す」と書くことが多い。今回の 3 件のうち 2 件がそうだった。
- 問題: 要求を出すと、仕様の更新と全工程の再確認が要る。実害の無い文面の直しまで要求の候補になり、整理の段階で毎回取り下げることになる。
- 提案: issue の書式に「要求を出さない場合の実害(実装・運用で何が困るか)」の 1 行を必須にする。実害が「なし」なら、提案は「記録のみ」とする。
- 根拠: 利用者の 2026-11-18 の方針(仕様への要求は、出さないと実害が出るものだけにする)。先行機能でも、性能についての要求 2 件を公開せず取り下げた。

## 提案 2: 後続の機能のコマンドを起動する scenario の扱いを、スキルの手順に書く

- 現状: 全 scenario の pass を求めるゲートに、担当外のコマンドを起動する scenario の扱いが書かれていない。今回はオーケストレータがその場で決めた。
- 提案: 次の扱いを手順に足す。
  - 担当外のコマンドが無い間、該当の step は skipped を返す。
  - コマンドができたのに step が未実装なら、失敗させる。
  - 代役のコマンドは作らない。
  - skipped は pass の件数に含めず、scenario 名・保留を始めた行・担当の機能を完了の記録に書く。
  - 担当の機能の実装のときに、保留元の feature も合わせて流す。
- 根拠: `learnings/20261118_023215_scenario-owned-by-later-feature-skip-not-fake.md`

## 提案 3: 入口だけを作る段階の「仮の扱い」を、前提の記録で区別できるようにする

- 現状: 前提の記録には、「完成時もこのままの判断」と「後続の機能が置き換える仮置き」の区別が無い。今回の「正しい引数なら終了コード 6」は仮置きだが、ほかの前提と同じ並びで記録された。
- 問題: 最後の確認で、利用者が「いま決めること」と「後で置き換わること」を見分けにくい。
- 提案: 前提の記録に、任意の項目「仮置き(置き換える機能の名前)」を足す。確認用の資料は、仮置きを別の表に分けて見せる。
