# 後続の機能のコマンドを起動する scenario は、代役を作らず skipped にする

## 何が起きたか

- この機能の scenario のうち 3 件(tier 1 件、UC 2 件)が、`facade.sh` を起動する。
- `facade.sh` は次の機能の担当で、この機能の時点では存在しない。
- 全 scenario の pass を求めるゲートを、そのままでは通せなかった。

## 原因

- 仕様の scenario は、機能の単位ではなく「利用者から見た一連の操作」で書かれている。
- そのため、1 つの scenario に、複数の機能の責務が混ざることがある。

## 回避方法

- テストの骨組みを作る時点で、scenario の各行の担当の機能を判定し、issue に一覧として記録する。
- 担当外のコマンドを起動する step は、次の形にする。
  - コマンドが無い間は、cucumber の skipped を返す。
  - コマンドができたのに step が未実装なら、失敗させる(後続の機能での実装漏れを防ぐ)。
- 代役のコマンドは作らない。コマンドの振る舞いそのものが判定の対象のため、代役で通すと何も確かめないことになる。
- skipped は pass の件数に含めず、件数と理由を完了の記録に書く。
- 仕様の scenario の分け方を直す要求は出さない(実害が無いため。利用者の 2026-11-18 の方針)。

## 次回の対応

- 次の機能(slot 実行モードを選択して runner を起動する)で `facade.sh` を作ったら、この機能の feature も合わせて流す。保留の 3 件が pass になることを確かめる。
- 保留の一覧: `docs/impl/latest/65b09d93/issues/20261118_012630_cross-uc-scenarios.md`
