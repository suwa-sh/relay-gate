# bash で起動した子の「起動できなかった」は、開始の合図つきの通信路で知らせる

## 何が起きたか

- `facade.sh` は runner を `&` で起動し、プロセス番号を得た時点で「起動した」と扱っていた。
- 独立した検証の 1 回目で、次の指摘を受けた(重大)。
  - 実行権限はあるが起動できない runner(1 行目に書いたインタープリタが存在しない)でも、facade が終了コード 0 で終わる。
  - 管理 DB の slot の行が「実行中」のまま残る。
- 2 回目の実装で、起動の成否を子から親へ知らせる通信路(名前付きパイプ)を入れた。
- 独立した検証の 2 回目で、もう 1 件の指摘を受けた(重大)。
  - セッションを切り離すコマンド(`setsid`)自体が失敗すると、起動していないのに成功として扱う。

## 原因

- `&` で起動した時点のプロセス番号は、途中の層(サブシェル)のものである。runner への切り替え(exec)が成功したかどうかは、親からは分からない。
- 2 回目の実装は「通信路が何も書かれずに閉じたら成功」と判定した。見張りの層が始まる前に失敗した場合も、同じく何も書かれずに閉じるため、区別できなかった。
- bash 5.2(実行環境の Ubuntu 24)は、失敗した exec に付けたリダイレクトを元に戻さない。「exec のリダイレクトで通信路を閉じる」方式は使えなかった(bash 5.2.21 と 5.3.15 で実測)。

## 回避方法

- 起動のたびに、権限 0600 の一時ディレクトリへ名前付きパイプを作る。
- runner へ切り替える層は、次の順で動く。
  1. 見張り役(coproc)を始める。
  2. 最初に「見張りを始めた」という合図の行を書く。
  3. runner へ exec する。成功すると、exec で自動的に閉じる通信路(close-on-exec)が閉じる。
- 親は 3 通りを区別する。

| 親が受け取ったもの | 判定 |
|---|---|
| 合図の後に、何も書かれずに閉じる | 起動の成功 |
| 合図の後に、失敗の行 | 起動の失敗 |
| 合図が無いまま閉じる、または合図以外の行 | 起動の失敗(見張りの層より前で失敗した) |

- runner の終了は待たない(background を待たない、という仕様を守る)。
- テストは、存在しないインタープリタの runner、不正な実行形式の runner、失敗する `setsid` の 3 つで確かめる。

## 次回の対応

- 子プロセスを起動する処理を新しく書くときは、最初から「開始の合図 → 成否」の 2 段で設計する。「何も届かなければ成功」という判定にしない。
- 速報クロスチェックの runner やワーカーを起動する後続の機能では、`facade/src/gateway/runner_process_adapter.sh` の方式を再利用する。
- macOS と Linux で bash の版が違う。exec とリダイレクトの挙動は、両方で実測してから採用する。
