# 「A の後に B」を確かめるテストは、順を入れ替えた実装で落ちることまで確かめる

## 何が起きたか

- 仕様は「slot の行を管理 DB に追加してから、runner を起動する」と定める。
- この順を確かめるシナリオは、「行の追加の記録」と「runner が書いた起動の記録」の並びを見ていた。
- 独立した検証の 2 回目で、次の指摘を受けた。
  - 行の追加を起動の後へ移した実装(複製に入れた変異)でも、このシナリオは通る。

## 原因

- runner が起動の記録を書くのは、起動されてから少し後である。
- そのため、実装が「起動 → 行の追加」の順でも、記録の並びは「行の追加 → 起動の記録」になり得る。
- 別々のプロセスが書く記録の並びだけでは、処理の順を確かめられない。

## 回避方法

- 順を作る側に、短い待ちを入れる。
  - テスト用の DB クライアントは、行の追加を記録する前に 1 秒待つ(テストのときだけ)。
  - テスト用の runner は、動き出した時点で「記録済みの行の追加の数」を書く。
- 正しい実装では、runner が動き出した時点で、自分の slot の行の追加が記録済みである。
- 順を入れ替えた実装では、runner が先に動き出すため、数が足りずに落ちる。
- 待ちは順を作るためのもので、時間を測ってはいない。負荷が高くても、正しい実装が落ちない向きの判定にする(「1 件以上」で判定する)。
- 一時的な複製に変異を入れ、3 回流して 3 回とも落ちることを確かめた。

## 次回の対応

- 順を確かめるテストを書いたら、順を入れ替えた複製で落ちることを 1 回確かめる。
- 確かめた結果(入れ替えた内容と、落ちた判定の行)を、完了の記録に書く。
- 後続の機能にも、順が仕様で決まっている処理がある(完了の通知、結果の公開)。同じ方法を使う。
