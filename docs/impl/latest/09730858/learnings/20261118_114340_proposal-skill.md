# スキルへの提案(distillery-impl)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。

## 提案 1: 「仕様に記載なし」の前提の確認記録を、実装の指摘と別の件数で数える

- 現状: 独立した検証は、前提 1 件ごとに確認記録を 1 件作る。安全性とデータの保存の前提は、重さが「major」になる。
- 問題: 今回の 3 回目は、実装の欠陥が 0 件なのに「major 7 / minor 15」と記録された。件数だけを見ると、未解決の問題が 7 件あるように読める。実装者も、3 回とも同じ 20 件前後に「対応不要」と書き続けた。
- 提案: 検証の結果の件数を、「実装の指摘」と「前提の確認記録」に分ける。通過の判定と再実装の入力には、実装の指摘だけを使う。
- 根拠: `stages/attempt-3/S5_verify.tier-facade.done.yaml`(「major 7 / minor 15 はすべて前提照合の必須記録」)

## 提案 2: オーケストレータが決めた前提に、「決定済み」の印を付けられるようにする

- 現状: 前提の記録には、「実装者が自分で決めた」と「オーケストレータの指示で決めた」の区別が無い。今回の「管理 DB へのつなぎ方」は後者だが、理由の文の中にしか書かれていない。
- 問題: 検証者へ「決定済みなので欠陥として扱わない」と毎回文章で伝える必要があった。確認用の資料でも、手で分けて見せる必要がある。
- 提案: 前提の記録に、任意の項目「決めた主体(実装者 / オーケストレータ / 利用者)」を足す。確認用の資料は、主体ごとに表を分ける。

## 提案 3: 子プロセスを起動する実装の確認項目を、検証の観点に足す

- 現状: 今回の重大な指摘 4 件のうち 2 件は、「起動できなかったことを検知できない」ものだった(2 回に分かれて見つかった)。
- 提案: 実装のスキルと検証のスキルに、次の確認項目を足す。
  - 起動の成功を、「何も届かなければ成功」で判定していないか。
  - 起動用のコマンド自体の失敗、インタープリタの不在、不正な実行形式の 3 つをテストしているか。
  - 親の環境にある同名の変数が、子へ渡らないことをテストしているか。
- 根拠:
  - `learnings/20261118_114340_bash-exec-failure-needs-start-signal-handshake.md`
  - `learnings/20261118_114340_parent-exported-vars-leak-to-child.md`

## 提案 4: 順を確かめるテストは、順を入れ替えた複製で落ちることを確かめる

- 提案: 実装のスキルの手順に、「仕様が順を定める処理のテストは、順を入れ替えた一時的な複製で落ちることを 1 回確かめ、結果を完了の記録に書く」を足す。
- 根拠: `learnings/20261118_114340_order-assertion-needs-sync-and-mutation-check.md`

## 提案 5: 検証者が追加の比較を流すときは、一時ディレクトリを分ける

- 現状: 3 回目の検証で、単体テストの全件実行と、変更前後の比較を同時に流した。一時ファイルの名前がぶつかり、単体テスト 1 件が失敗した(単独の実行で通過)。
- 提案: 検証のスキルに、「ゲートの再実行と追加の検証は、同時に流さない。流すなら一時ディレクトリ(`TMPDIR`)を分ける」を足す。
