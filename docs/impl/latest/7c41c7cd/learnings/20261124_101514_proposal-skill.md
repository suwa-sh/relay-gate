# スキルへの提案(distillery-impl)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。
前回の提案(`learnings/20261123_175902_proposal-skill.md`)に足す分だけを書く。

## 提案 1: 「同じ形の箇所も直す」の探し方を、操作で指定する

- 現状: 欠陥を直すときに同じ形の箇所を探したが、探す範囲が機能の名前(入力の複製)だったため、同じ操作(`mv`)を使う別の箇所が残った。やり直しが 1 回増えた。
- 提案: 実装のスキルの「指摘を直す」手順に、次を足す。
  - 原因になった操作(コマンド・関数・書き方)を、対象のディレクトリ全体で検索する。
  - 探した語、範囲、見つかった件数を、完了の記録に書く。
- 根拠: `learnings/20261124_101514_same-shape-search-by-operation-not-by-feature.md`

## 提案 2: 前提の番号を使い回さない

- 現状: やり直しで、同じ番号の前提が別の内容になった(2 件)。前回の人の承認が、今回の内容にも及ぶように見える。
- 提案
  - 前提の検査(`validateAssumptions.js`)で、前の回の同じ番号と文面が大きく違うときに警告を出す。
  - 前提の記録に、任意の項目「前回の確認との対応(同じ / 変わった / 新規)」を足す。
  - 最後の確認の資料は、文面が同じ前提だけを「前回承認済み」と表示する。
- 根拠: `learnings/20261124_101514_assumption-id-reuse-hides-content-change.md`

## 提案 3: 検証の観点に「確定名に先客がある場合」を足す

- 現状: 「一時名へ書いて確定名へ移す」処理の欠陥が、自動のセキュリティ確認と 4 回目の検証まで見つからなかった。
- 提案: 検証のスキルの障害への強さの観点に、確認項目を足す。
  - 一時名から確定名へ移す処理で、確定名にディレクトリ・リンクが先にある場合の結果を、実ファイルで確かめたか。
  - 仕様が約束する結果(公開しない、失敗にする)と一致するか。
- 根拠: `learnings/20261124_101514_mv-success-does-not-prove-final-name.md`

## 提案 4: 「仕様に記載なし」の確認記録を、実装の指摘と別の件数で数える(再掲。3 回目)

- 現状: 5 回目の検証は、実装の欠陥が 0 件なのに「重い 5 件 / 軽い 19 件」と記録された。
- 提案: 検証の結果の件数を、「実装の指摘」と「前提の確認記録」に分ける。
- 根拠: `stages/attempt-5/S5_verify.tier-facade.findings.yaml`(24 件のうち、実装の指摘は 0 件)

## 提案 5: 前提の分類の判定を、回をまたいで安定させる

- 現状: 同じ前提(runner も一時複製で読む)を、4 回目の検証は「安全性」、5 回目の検証は「データの保存」と判定した。実装者は 4 回目の判定に合わせて直したため、5 回目で再び分類の違いが記録された。
- 提案: 検証は、前の回の検証が確定した分類を入力として受け取り、変える理由があるときだけ変える。または、回答が必須かどうかが変わらない分類の違いは、指摘として数えない。
- 根拠: `stages/attempt-4/S5_verify.tier-facade.findings.yaml` の F-020、`stages/attempt-5/S5_verify.tier-facade.findings.yaml` の F-024
