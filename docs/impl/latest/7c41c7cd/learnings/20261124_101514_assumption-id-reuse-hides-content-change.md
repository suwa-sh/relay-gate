# 前提の番号を使い回すと、承認済みの内容と入れ替わったことが見えない

## 何が起きたか

仕様の反映の後に実装をやり直したところ、前提の記録のうち 2 件が、同じ番号のまま別の内容になった。

| 番号 | 前回の確認で承認した内容 | 今回の内容 |
|---|---|---|
| A-029 | 一時複製の名前にプロセスの番号を入れる | 一時複製を最終名へ移すときの確認(先客があれば失敗) |
| A-026 | 二重起動の判定の関数の呼び方 | その関数を単独で呼んだときは、実行ログに警告を書かない |

番号だけを見ると「前回承認済み」に見える。実際には、今回の内容に対する人の判断はまだ無い。

## 原因

- 前の内容が仕様に入ったとき、実装者は「残った自分の判断」や「同じ場所の新しい判断」を、同じ番号で書き直した。
- 前提の記録には、前回の確認との対応(同じ / 変わった / 新規)を書く欄が無い。

## 回避方法

- まとめの段で、前回の確認の対象だった記録と今回の記録の文面を機械的に比べ、「同じ / 文面が変わった / 新規 / 無くなった」を一覧にした。
- 最後の確認では、番号ではなく内容の名前で示し、「前回承認済み(同じ内容)」と「今回が初めて」を分けて回答を求める。

## 次回の対応

- 内容が入れ替わる前提には、新しい番号を付ける。古い番号は欠番にする。
- 仕様の反映の後のやり直しでは、前回の人の判断をそのまま引き継がない。文面が同じ前提だけを「前回承認済み」と表示する。
- 根拠: `stages/attempt-5/S4_tier-impl.tier-facade.assumptions.yaml`、`invalidated/` 配下の前回の 4 回目の前提の一覧、`review/review-notes.md`
