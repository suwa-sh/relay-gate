# 保留にするテストは、この機能で決まる部分を判定してから保留を返す

## 何が起きたか

- この機能が作るのは「解決」の段だけで、解決結果を外へ出す段(実行の指示書の保存、実装の実行)は後続の機能が作る。
- 結合テスト 1 件と受け入れテスト 1 件は、後続の段が無いと最後まで判定できない。
- 単純に保留にすると、解決が壊れていても「保留」と表示され、失敗に気づけない。
- 実際に、一時複製の名前がぶつかる不具合は、保留にしていたシナリオで起きた。保留の前に解決の成否を判定していたため、失敗として表に出た。

## 原因

- テストの道具は、保留を返した手順より後ろを実行しない。保留の手順が何も確かめないと、そのシナリオは何も守らない。
- 機能を順に作る進め方では、機能をまたぐシナリオが必ず出る。

## 回避方法

- 保留を返す手順の中で、先に「この機能で決まる部分」を判定する。今回は次の 2 つ。
  - 解決に成功したこと(実行ログの解決の行)
  - 組み立てた引数の並び(共通ライブラリを直接呼ぶ)
- 保留を返す条件を狭くする。「解決に成功していて、後続の段の成果物がまだ無い間だけ」にする。解決に失敗した回は、保留にせず失敗させる。
- 後続の機能が成果物を書くようになると、同じ手順がそのまま残りを判定する(手を入れなくても保留が外れる)。
- 保留の条件、判定した部分、保留が外れる条件を、完了の記録に書く。

## 次回の対応

- 後続の機能の結合テストと受け入れテストで、今回の保留 2 件が外れることを確かめる。
- 新しく保留を作るときも、同じ形(先に判定、条件は狭く、外れる条件を記録)にする。
- 保留のシナリオが不安定に失敗したら、保留のせいにせず、判定している部分の不具合を疑う。
