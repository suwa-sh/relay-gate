## 1. 何が起きているか

この機能が作るのは、runner の「解決」の段だけである。解決に成功した後の段(execution-spec.json の保存、実装の実行)は後続の機能が作る。

| 段 | 担当する機能 | この機能の完了時点 |
|---|---|---|
| 引数の検査、ジョブマップの読み込み、実行先の解決、引数列の組み立て | この機能(7c41c7cd) | ある |
| 解決に失敗したときの 3 ファイルと started-at.txt | この機能(7c41c7cd) | ある |
| execution-spec.json の保存 | 43850d68(execution-spec.json を確定保存する) | 無い |
| 実装の実行(ローカル / SSH)、実装へ引数を渡す、Runner Result の出力 | 5ebe8db7(実装スクリプトを実行して Runner Result を出力する) | 無い |

このため、runner を 1 つのプロセスとして起動しただけでは、解決に成功したときの結果のうち外から見えるものが実行ログの 1 行(`job map resolved job_id=... slot=... host=... map_version=...`)しか無い。user / script / work_dir / hang_detect_limit_minutes / credential_ref / fixed_params / 引数列は、この行に出ない。

## 4. 決めること: 解決結果を何で確かめるか

仕様の記載:

- spec.md 概要・tier-facade.md 変更概要: 解決ロジックは共通ライブラリ(`lib/runner-*.sh`)に置き、利用者が自作する runner も同じライブラリを `source` すれば同じ解決になる
- CLI 契約 `standard_runner.custom_runner`: 自作の runner は共通ライブラリ 4 ファイルを source して使える

仕様に無いもの:

- 共通ライブラリの関数の名前、引数、解決結果の受け取り方(変数か、出力か)。自作の runner が使う入口なのに、呼び方がどこにも書かれていない
- 解決に成功した後、後続の段がまだ無い間の runner の終わり方(終了コードと成果物)。tier-facade.md の終了コード表は「0 = 解決成功。次フェーズへ進む。最終的に実装の exitcode.txt と一致させる」で、次フェーズが無い時点の振る舞いは書かれていない

選択肢:

| 案 | 内容 | 仕様の変更 | この機能で判定できる範囲 |
|---|---|---|---|
| A(推奨) | step と単体テストが共通ライブラリを source して関数を直接呼び、解決結果と引数列を確かめる。関数の名前と受け取り方は実装者が決め、補った前提として S4 の記録に書く。あわせて S8 で「共通ライブラリの呼び方を仕様に書く」要望を出す | 要望 1 件(S8) | 正常系 10 件の全項目 |
| B | 実行ログの行(host と map_version)だけで判定し、残りの項目は execution-spec.json ができる次の機能まで保留にする | なし | host と map_version だけ。残りは保留 |

推奨は A。tier-facade.md のティア完了条件が「CSV 行分解関数を呼ぶ」「引数連結関数を呼ぶ」「解決フェーズまで実行する」と、関数を直接呼ぶ前提で書かれているため。

解決に成功した後の終わり方は、前の機能と同じく「実装者が補った前提」として S4 の記録に書く(S2 の単体テストは、解決に成功したときの終了コードを判定していない)。
