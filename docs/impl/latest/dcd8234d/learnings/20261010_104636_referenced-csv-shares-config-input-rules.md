# 検証対象から参照する別の CSV にも、共通の入力規則が適用される

## 何が起きたか

- `--crosscheck-job-map` の検証ルール 9(対象カタログ参照の解決)は、参照先の対象カタログを読む。実装は「参照解決のみ(列検証は確報 tier に委ねる)」と読んで、参照先を読むときの入力の守備範囲(NUL / 不正な UTF-8 / BOM / CR / ヘッダー列名の重複 / クォート不正 / 空白だけの行)を適用しなかった。
- 独立検証は、参照先カタログに対する守備範囲の抜けを 3 回続けて blocker にした。

| attempt | 参照先カタログに関する blocker |
|---|---|
| 1 | バイト形式違反を参照未解決に置き換える(F-013)。重複列名を見逃し曖昧な列で参照解決する(F-022) |
| 2 | クォート不正のデータ行を無視する(F-007)。空白だけの行を受理する(F-018) |
| 3 | 1 列ヘッダーのカタログで半角空白だけの行を受理する(F-018) |

- attempt 4 で、解析後の行が 1 セルかつ空白だけの行をヘッダーの列数に関係なく拒否して収束した。

## 原因

- CLI 契約の `config_input_rules` は「設定ファイルを読むすべての読み手」に共通規則を課す。参照先を読む読み手も対象だが、tier 仕様の検証ルール 9 は「参照解決のみ」と書くため、実装者が「参照先の形式は見なくてよい」と読んだ。
- 実装は共有の CSV 解析関数の結果(解析後のセル)だけを見ており、「空白だけの物理行」を列数の比較(`actual -ne expected`)に置き換えていた。ヘッダーが 1 列のカタログでは `expected=1 / actual=1` で通ってしまう。
- 共有の解析関数は元の物理行を保持しないため、引用で囲んだ空白(`" "`)と物理行の空白を区別できない。境界を前提(A-024)として記録した。

## 回避方法

- 検証対象から別のファイルを読む処理を書くときは、「そのファイルも契約の入力規則の対象か」を先に確認する。`scope` が「すべての読み手」なら、参照先にも同じ関数(単一スナップショット・バイト点検・クォート解析)を通す。
- 共通規則の各項目(NUL / UTF-8 / BOM / CR / 重複列名 / クォート / 空白だけの行 / 列数)を参照先に対しても 1 項目ずつ bats にする。主ファイルのテストだけでは参照先の抜けを見つけられない。
- 「空白だけの行」のような規則は、契約の説明(1 セルのデータ行として列数不一致)をそのまま列数比較に置き換えない。規則の意図(空白だけの物理行を拒否)を直接判定する。
- 独立検証が同じ観点(参照先の守備範囲)で 2 回続けて blocker を出したら、3 回目を待たずに観点全体を洗い直す(項目を 1 つずつ直すと attempt を消費する)。

## 次回の対応

- 別ファイルを参照する検証(各 env 設定からの runner 参照、対象カタログからの比較定義参照など)では、着手時に「参照先に適用する入力規則の一覧」を前提記録の冒頭に書く。
- 参照先の列数不一致の `expected` の基準は仕様側に求めた(CR-dcd8234d-005)。
