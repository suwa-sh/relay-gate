# 仕様策定の仮採用(推論)が実装まで進んでから、方針資料と照合して外れた

## 何が起きたか

- 本 UC の確報側(対象カタログ CSV の列定義・`validate-config.sh --target-catalog` の検証・速報側の対象カタログ参照の解決)を、仕様どおりに実装し、独立検証 4 回と UC BDD / ATDD を通した。
- S9 のレビュー対話で、利用者が「target-catalog.csv は何の対象か。クロスチェック自体は別ツールが行うので対象一覧は不要」と問い、方針資料と照合した結果、対象カタログと business_date を relay-gate から外す決定(案 A)になった。
- 確報ティアの実装(bats 57 件)と速報ティアの検証ルール 9 の実装は、仕様反映後に削除される。

## 原因

- 方針資料は「比較対象の定義は、適用側で定義します」とだけ定め、確報依頼のデータ項目に「business_date」「対象カタログの版」を挙げていた。仕様策定フェーズは、この 2 項目から対象カタログの列・検証・比較ツールへの受け渡しを推論し、仮採用(`_inference.md` #5)として仕様化した。
- 仕様には「所在は `_inference.md` #5 仮採用」「仮採用: 確報比較ツールへの引数の渡し方は方針資料に定めが無いため」の注記があった。実装フェーズは注記を「仕様として確定済み」と読み、実装前に利用者へ確認しなかった。
- 実装・独立検証・BDD はいずれも「仕様どおりか」を判定する。仕様自体が方針資料と乖離していることは、人が方針資料と照合するまで見つからない。

## 回避方法

- 着手する UC の spec.md / tier-*.md / 契約に「仮採用」「推論」「`_inference.md` #N」の注記がある設定ファイル・外部 IF は、実装前に利用者へ「この仮採用を実装してよいか」を確認する。確認の材料は、方針資料の該当箇所と仕様の記述の対比(1 ページ)でよい。
- 特に「relay-gate が何を持つか」(設定ファイル・DB 列・比較ツールへ渡す引数)に関わる仮採用は、実装後に外すと削除範囲が複数 UC に及ぶ。実装前の確認コストのほうが小さい。
- 仮採用の確認は、S9 の前提(AssumptionRecord)のレビューとは別物として扱う。前提は「仕様に無いことを実装者が補った」もので、仮採用は「仕様策定が方針資料に無いことを補った」ものである。後者は仕様の文言を読んでも実装者には判別しにくいため、注記の有無で機械的に拾う。

## 次回の対応

- UC 着手時(S1 相当)に、対象 spec と契約の該当箇所から「仮採用」「`_inference.md`」の注記を `rg` で抜き出し、該当があれば利用者確認を S1 の完了条件に含める。
- 残りの UC で同じ注記を持つ設定ファイル・外部 IF(例: 確報 runner の polling 既定値 `_inference.md` #6、`input/target-catalog.csv` の抜き出し)は、本決定(案 A)の反映後に再確認する。
- 一般化した提案(S1 で仮採用注記を抜き出して利用者確認にかける)は `learnings/20261010_104636_proposal-skill.md` の末尾に追記した。
