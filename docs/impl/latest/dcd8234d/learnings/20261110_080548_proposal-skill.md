# スキルへの改善提案(dcd8234d、還流 run 2〜9 後の再実装)

既存の SKILL.md は変更していない。採否は人が判断する。前回(`20261027_091000_proposal-skill.md`)の提案は繰り返さない。

## 提案 1: 還流後の UC 初期化で、受け入れテストの対応づけの差分を確認する

- 対象: distillery-impl の dist-impl-run(UC 初期化)
- 事象: 還流で受け入れ基準 -12 が増え、-10 の文言が変わったが、uc-map の対応づけは確認済みの 6 件のままだった(learnings `20261110_080548_reflux-requires-atdd-mapping-followup.md`)
- 提案: UC 初期化で、対象要求の feature のタグ一覧と `atdd_scenarios` を突き合わせ、追加・削除・文言変更を列挙する手順を加える。追加は機械的な追従として記録し、最終レビューで利用者に示す

## 提案 2: 還流の後、同じ共通規則を使う完了済み UC の未追従を検出する

- 対象: distillery-impl の dist-impl-run(UC 選択・UC 初期化)と dist-impl-verify
- 事象: env の共通規則の還流で、完了済み UC「feature flag を設定する」が未追従になっていた。見つかったのは独立検証が範囲外の観察として実走したからで、計画された経路ではない(learnings `20261110_080548_completed-uc-drift-after-reflux.md`)
- 提案:
  - 還流後の最初の UC 初期化で、completed の UC ごとに「仕様の tier BDD Scenario 数」と「tier BDD feature の Scenario 数」を比べ、不一致を一覧にする
  - 決定記録(spec-decision)が影響 UC を挙げている場合は、その UC を再実行の候補として status に印を付ける

## 提案 3: 共有関数を変えるときは、呼び出し元 UC の確認を tier 実装の完了条件にする

- 対象: distillery-impl の dist-impl-implement(tier-impl)
- 事象: バイト検査の報告関数を仕様どおりに直したら、完了済み UC の `--job-map` の出力順も変わった。呼び出し元 UC の tier BDD に該当 Scenario が無く、bats を足して判定した(learnings `20261110_080548_shared-function-fix-changes-completed-uc-output.md`)
- 提案: write-set 内の共有関数を変える場合、呼び出し元を列挙し、UC ごとに「出力が変わるか / テストで判定されているか」を完了記録に書くことを必須にする

## 提案 4: 前提の抽出で「仕様に文言が無い出力行」を候補に必ず含める

- 対象: distillery-impl の dist-impl-implement(tier-impl の前提の抽出)
- 事象: `--verbose` の info 行の順と出す条件は前提として記録されたが、info 行の文言そのもの(`info: key loaded ...`)も仕様に無かった。独立検証の判定と変更要求の作成で初めて文言の欠落が表に出た
- 提案: 実装が出す stdout / stderr の各行の文言を仕様と照合し、仕様に無い文言を前提の候補に入れる確認項目を加える(順・条件だけでなく文言も)
