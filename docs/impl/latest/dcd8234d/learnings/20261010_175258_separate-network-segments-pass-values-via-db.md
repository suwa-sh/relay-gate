# 別ネットワークセグメントの runner / worker 間では、ファイルパスを受け渡しに使えない

## 何が起きたか

- 仕様は、速報の完了通知が成果物ディレクトリの URI(`artifact_uri`)を DB に保存し、速報 worker が比較定義の `{blue}` / `{green}` をその URI に置換して比較ツールへ渡す構成だった。確報 worker も対象カタログの該当版を `input/target-catalog.csv` としてファイルに書き出して渡し、両 worker とも比較ツールの stdout / stderr / exitcode を runner 側の成果物ディレクトリにファイル保存する契約だった。
- 第 2 回のレビュー対話(2026-10-10)で、利用者から「runner と worker は別ネットワークセグメントで動く。worker はファイルパスを渡されても読めない」という想定環境の制約が示された。成果物パスの受け渡しと worker 側のファイル保存は、この環境では成立しない。
- 本 UC の実装(比較定義 CSV の検証、プレースホルダ `{blue}` `{green}` の必須検証、対象カタログの検証)は、この構成を前提に作られており、簡素化の反映後に削除される。

## 原因

- 方針資料は「worker は stdout / stderr / exitcode を依頼レコードへ保存する」「比較対象の定義は適用側で定義する」と定めるだけで、runner / worker 間の共有ファイルシステムの有無を明記していなかった。仕様策定フェーズは、facade と runner が共有する成果物ディレクトリの規約(Runner Result Contract)を worker にも延長して推論した。
- 実装フェーズは仕様の構造(ファイルパスの受け渡し)を所与として検証ルールを実装し、「worker はそのパスを読めるか」という配置の前提を問わなかった。

## 回避方法

- プロセス間で値を受け渡す仕様を実装する前に、「送り手と受け手が同じファイルシステムを見えるか」を配置図(方針資料の C1 Context / DB セグメント構成)で確認する。別セグメントなら、受け渡しは DB の依頼レコード(または明示的な転送)に限り、ファイルパスを渡さない。
- 「worker に必要な情報は DB の依頼レコードに含める」を速報・確報の依頼レコードの設計原則として扱う。レコードに無い値を worker が必要とする仕様(成果物 URI、カタログのパス、設定ファイルの行の参照)が出てきたら、配置の前提を利用者に確認する。
- 比較ツールに渡す値は依頼レコードの値だけ(job_id / run_id / parameters / 両系の exit_code)にし、relay-gate 側で比較対象やファイルの所在を解決しない。

## 次回の対応

- 速報・確報の worker 系 UC を実装するときは、worker が読む入力を「自分の設定ファイル」と「DB の依頼レコード」の 2 つに限定し、それ以外のファイル参照(成果物ディレクトリ・対象カタログ)が仕様に残っていれば変更要求に戻す。
- `execution-spec.json` や Runner Result の成果物を参照する UC(ハング検知・リラン・中止)は facade / runner と同じセグメントで動く前提である。worker 系 UC と同じ扱いにしない。
- 一般化した提案(配置の前提を UC 着手時に確認する)は `learnings/20261010_104636_proposal-skill.md` の末尾に追記した。
