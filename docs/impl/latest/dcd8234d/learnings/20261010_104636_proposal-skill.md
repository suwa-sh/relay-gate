# スキル改善の提案(dist-impl-run / dist-impl-implement / dist-impl-verify)

既存の SKILL.md は変更していない。取り込むかどうかは保守者が判断する。

## 提案 1: 同じプロセスに source される tier の関数名の衝突検出を統合ゲートに入れる

- 現状: S4 のゲート(format / lint / tdd / bdd_tier)は tier 単独で実行される。tier 間の関数名の衝突は、bash が黙って上書きするため lint でも単体テストでも検出されない。
- 問題: 速報クロスチェック tier の関数 `target_catalog_repo_load` が確報 tier の同名関数に上書きされ、実プロセス経由のテストでだけ終了コード 6 になった(`issues/20261010_092630_tier-handler-function-namespace-collision.md`)。
- 提案:
  - `impl-config.yaml` の tier 定義に任意の `symbol_prefix`(例: `crosscheck_`)を持てるようにし、S4 の lint ゲートの後で「tier の src 配下で定義するトップレベル関数名・グローバル変数名が接頭辞で始まること」を検査する。
  - S6(UC BDD)の前に、同じ UC の全 tier の `declare -F` の集合を比較し、重複があれば fail にする(kind: cli かつ lang: bash の tier だけ)。
  - 未定義のときは現状どおり。

## 提案 2: 契約に無い tier 間依存を S2 で見つけたときの既定の扱いを SKILL.md に書く

- 現状: S2 test-scaffold が「仕様どおりに実装すると write-set の外(他 tier)を変えないと動かない」事実を issue にし、オーケストレータが既定 ③(issue 起票つきの意図的逸脱で統合を通し、S8 で変更要求化)を選んだ。選択肢(write-set の例外 / 他 tier 側の拡張フック / uc-map の tiers 追加で S1 やり直し)は issue の中で実装者が列挙した。
- 問題: 既定 ③ の存在と、単一 writer(オーケストレータ)が他 tier に最小の登録を 1 commit で入れる手順が、SKILL.md から読める形になっていない。次の UC でも同じ判断を一から組み立てる。
- 提案: dist-impl-run の S2 → S3 の間に「cross-tier 依存の扱い」を 1 節置き、(1) issue 起票の必須項目(契約に無い依存面・影響する write-set・選択肢)、(2) 既定 ③ の条件(他 tier への変更が登録・結線だけで、ロジックを含まない)、(3) オーケストレータが単一 writer として入れる commit の形式、を書く。

## 提案 3: Verifier の blocker が同じ観点で 2 回続いたら、観点全体の再点検を Implementer に指示する

- 現状: S4 の再実行は、直前の S5 findings の blocker を個別に修正する。attempt 2 以降の blocker 3 件はすべて「参照先カタログへの共通入力規則の適用」という 1 つの観点に属し、項目を 1 つずつ直したため attempt 上限に到達した。
- 問題: 項目単位の最小修正は、同じ観点の別項目を次の attempt に持ち越す。
- 提案: dist-impl-run が attempt N+1 を開くとき、attempt N と N-1 の blocker の `viewpoint` / 対象ファイルが同じなら、S4 の可変プロンプトに「同じ観点の規則を全項目洗い直し、各項目の bats を追加する」指示を加える。Verifier には「同じ観点で残る項目を全件列挙する」ことを求める(1 件ずつ出さない)。

## 提案 4: tier BDD の Given / Then の不一致を S2 で検出して issue にする

- 現状: tier 仕様の BDD「compare_options にプレースホルダが無い」は Given(`--fast`)と Then(`value=--blue {blue}`)が両立せず、S4 の実装者が step 定義で代替した(`issues/20261010_093000_tier-bdd-placeholder-scenario-given-then-mismatch.md`)。
- 問題: 転写規約で feature を直せないため、代替は step 定義に埋まり、仕様の矛盾が S8 まで見えにくい。
- 提案: S2 test-scaffold の転写時に、Then の `value=` などの引用値が同じ Scenario の Given に現れない場合を「Given / Then 不一致の候補」として issue に列挙する(機械判定は候補の提示まで。最終判断は実装者)。S6 done の `given_then_mismatch` フィールドと同じ形式で S2 done にも記録する。

## 提案 5(2026-10-10 refresh で追記): S1 で「仮採用」注記のある設定ファイル・外部 IF を抜き出し、実装前に利用者確認にかける

- 現状: 本 UC の確報側(対象カタログ CSV の列定義・`--target-catalog` の検証・参照解決)は、spec / tier md に「所在は `_inference.md` #5 仮採用」「仮採用: 確報比較ツールへの引数の渡し方は方針資料に定めが無いため」の注記があったが、S1 はこれを拾わず、S4 の実装・S5 の独立検証 4 回・S6 / S7 を通してから、S9 のレビュー対話で方針資料との乖離(比較対象の定義は適用側)が判明し、確報側の実装が削除対象になった(`learnings/20261010_172853_tentative-spec-confirm-before-impl.md`)。
- 問題: 実装・独立検証・BDD はすべて「仕様どおりか」を判定するため、仕様自体が方針資料と乖離していても S9 まで人の目に触れない。実装後に外すと削除範囲が複数 UC に及ぶ。
- 提案: dist-impl-run の S1(uc-init)で、対象 UC の spec.md / tier-*.md / shared_spec_refs の契約から「仮採用」「`_inference.md`」「推論」の注記を機械的に抜き出し、設定ファイル・DB 列・外部ツールへ渡す引数に関わるものがあれば、S2 の前に利用者確認(方針資料の該当箇所と仕様の対比 1 ページ)を S1 done の完了条件にする。確認結果は S1 done に `tentative_spec_confirmations` として記録し、S8 refresh の入力にもする。
