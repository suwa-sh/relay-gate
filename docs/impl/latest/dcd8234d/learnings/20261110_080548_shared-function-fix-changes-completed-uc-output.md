# 共有関数を直すと、完了済みの別 UC の出力も変わる

## 何が起きたか

- 仕様の決定(同じ行のバイト違反は NUL → UTF-8 → BOM → CR の順に出す)に合わせ、バイト検査の報告関数を直した
- この関数は `facade/src/usecase/validate_job_map.sh` にあり、完了済み UC「slot ごとのジョブマップを定義する」の `--job-map` 検証も使っている。直した結果、`--job-map` の出力順も変わった
- 完了済み UC の tier BDD には、この順を判定する Scenario(仕様の 33 件目)が無かったため、tier BDD では変化を検出できなかった。bats にテストを 1 件足して `--job-map` 側の順を判定した

## 原因

- 共有関数の呼び出し元が、今回の UC の write-set の外にある
- 完了済み UC のテストが仕様の Scenario を全件持っていない(33 件中 32 件)と、変化が仕様に近づいたのか離れたのかをテストで確かめられない

## 回避方法

- 共有関数を変える前に、呼び出し元を `grep` で列挙し、UC ごとに「出力が変わるか」「その UC のテストで判定されているか」を表にする
- 判定されていなければ、今回の変更と同じ commit で呼び出し元側のテストを足す(今回は `validate_job_map.bats` に +18 行)
- 変わる UC と理由を、実装の段の完了記録と UC 横断の issue に書いておく

## 次回の対応

- テスト骨格の段で、共有関数への変更が予定されているなら、呼び出し元 UC の tier BDD と仕様の Scenario 数を突き合わせる
- 足りない Scenario は、呼び出し元 UC の再実行が必要な事実として as-built に記録する
