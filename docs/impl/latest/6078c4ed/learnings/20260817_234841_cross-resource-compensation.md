# file と DB の境界では補償を明示する

## 何が起きたか

execution-spec の atomic rename と DB 記録が別資源であるため、片方の成功後に他方が失敗すると成果物または RUNNING 記録だけが残り得た。

## 原因

filesystem と RDB をまたぐ原子的 transaction はなく、成功順序と失敗時の補償状態が明示されていなかった。

## 回避方法

DB 内の関連記録は単一 transaction にまとめ、ファイル作成、DB commit、外部起動の各境界で補償操作と診断用相関 ID を定義する。ファイルは一時ファイルから権限を設定して atomic rename する。

## 次回の対応

各境界の障害注入と中断をテストし、残留物、補償結果、再試行可能性を確認する。
