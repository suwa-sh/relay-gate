利用者が次の 2 点を決定した。

| 日付 | 利用者の決定(原文) |

| 2026-11-13 | 5,000行 8MB 10sec以内は パフォーマンスの目標値であって、入力を制限する仕様ではありません |

### 現在の仕様と問題

| 現在の記載 | 場所 | 問題 |

### 変更してほしいこと

1. 設定ファイルの検査の性能の記載を「目標値」と明記する。次の 3 点が読み取れるようにする。
   - 入力を制限しない(大きさを理由に拒否・警告しない)
   - 目標を超えても、検証の結果(終了コード・標準出力・標準エラー)は変わらない
   - 合否の検査にしない(目標を超えたことを、実装・テストの不合格の理由にしない)。「保証する」「合否を判定」という語を、目標値であることが分かる語に改める
2. 目標の大きさの条件を「5,000 行以内かつ 8 MB 以内のファイルを、内容によらず 10 秒以内」と書き足す。
3. runner の応答待ち(最大 9.2 秒)は、設定ファイルの検査の目標(10 秒)とは別に数えると書く。`runner_help_probe.response_time_budget` の「問い合わせ以外の検証と出力を 0.8 秒以内に収めれば 10 秒以内を満たす」の記述を、この数え方に合わせて直す。
4. 目標を、4 つの設定検証種別(`--feature-flag` / `--job-map` / `--rapid-crosscheck` / `--final-crosscheck`)のどれに適用するかを書く。

4 の選択肢は次のとおり。推奨は案 A。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A(推奨) | 4 つの検証種別すべてに同じ目標を適用する | 2026-09-21 の決定「閾値を機能ごとに考え直さない」と同じ考え方になる。目標を 1 か所から引ける | `--rapid-crosscheck` と `--job-map` は、数 MB の入力で目標との差が大きい(上の表)。差は目標との差として記録する |
| B | CSV 形式(slot ジョブマップ)と feature flag だけに適用する | 現在の記載(CSV 形式)からの変更が小さい | 速報・確報クロスチェック設定の目標が無いままになり、機能ごとに再び決める必要が出る |

### 完了条件

- 非機能要求グレードと CLI 契約のどちらを読んでも、「5,000 行以内かつ 8 MB 以内を内容によらず 10 秒以内」が目標値であり、入力の制限でも合否の検査でもないと分かる
- 5,000 行または 8 MB を超えるファイル、および目標の時間を超えた実行について、検証の結果が変わらないことが仕様に書かれている

- 目標を適用する検証種別が明記されている

## CR-fd678b04-002: `--feature-flag` のキーごとの検査で error 行が 2 行以上出るときの、error 行どうしの順を定める

- severity: spec-gap
- related_ids: [SPEC-001-01, REQ-001]
- related_files: [docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml, docs/specs/latest/適用構成業務/適用構成定義フロー/feature flag を設定する/tier-facade.md, docs/specs/latest/適用構成業務/適用構成定義フロー/feature flag を設定する/spec.md]

### 観測した事実

`validate-config.sh --feature-flag` の実装は、キーごとの検査の error 行を次の順で出す。この順は 2026-09 の完了時点から変えていない(独立した検証が、過去の 2 つの版と 436 条件で出力を比べ、差が無いことを確認した)。

1. `BLUE_MODE` → `GREEN_MODE` → `RAPID_CROSSCHECK_MODE` の必須・列挙
2. foreground の個数
3. `BLUE_IMPL` → `BLUE_RUNNER` → `GREEN_IMPL` → `GREEN_RUNNER`
4. `RAPID_CROSSCHECK_RUNNER` → `RAPID_CROSSCHECK_WORKER`
5. `FINAL_` で始まるキー(ファイルに出た順)
6. 対応ジョブマップ(blue → green)

テストは、error 行が 1 行だけになる入力を使うか、「含まれる」ことだけを確認している。error 行どうしの順を固定するテストは無い。

### 現在の仕様と問題

検査の段ごとに、順が決まっている範囲と決まっていない範囲は次のとおり。

| 段 | 行どうしの順 |
|---|---|
| バイト・改行の検査 | 決まっている(行番号の昇順) |
| 行の構造の検査 | 決まっている(形式違反の行を行番号の昇順 → 重複キーを初出行の昇順) |
| キーごとの検査の中の、行の種類の順 | 決まっている(info 全件 → 未知キーの warn 全件 → error 行 → runner の未応答の warn) |
| キーごとの検査の error 行どうしの順 | **決まっていない** |

- CLI 契約の `config_input_rules.env_files` は「error 行どうしの順は各検証種別の契約のとおり」と書く。`--rapid-crosscheck` は「検証ルールの表の順」と出所を書くが、`--feature-flag` は順の出所を書いていない
- `--feature-flag` の契約(`config_files` の feature-flag.env の `validation_rules` / `error_messages`、tier-facade.md のキー表と組合せ検証)は、規則と文言を列挙するだけで、順を定めていない
- 同じ `env_files` は「4 検証種別の `--verbose` は、どの入力・状態の組み合わせでも標準エラーの行数と内容を 1 つに決める」と書く。`--feature-flag` で error 行が 2 行以上出る入力では、この文が成り立たない
- BDD シナリオは、error 行が 2 行以上出る場面を「両方が出る」と書き、順を求めていない

元の方針資料には、検証コマンドの error 行の順の記載が無い。どちらの案も元の方針と食い違わない。

### 変更してほしいこと

`--feature-flag` のキーごとの検査の error 行どうしの順を、CLI 契約の feature-flag.env の節に 1 つに定める。tier-facade.md は同じ順を参照する。選択肢は次のとおり。推奨は案 A。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A(推奨) | 現行の順(上の 1〜6)を仕様に書く | 実装とテストが変わらない。2026-09 の完了時点から利用者に見えている順である | キー表の並び(mode → 実装版 2 つ → runner 2 つ)と違うため、順を別に覚える必要がある |
| B | キー表の順にする(`BLUE_MODE` → `GREEN_MODE` → `RAPID_CROSSCHECK_MODE` → `BLUE_IMPL` → `GREEN_IMPL` → `BLUE_RUNNER` → `GREEN_RUNNER` → `RAPID_CROSSCHECK_RUNNER` → `RAPID_CROSSCHECK_WORKER` → foreground の個数 → `FINAL_` で始まるキー → 対応ジョブマップ) | `--rapid-crosscheck` の「表の順」と同じ考え方になる | 実装の並べ替えが要る(検査の並びだけ。ほかの機能には及ばない)。利用者に見える順が変わる |

あわせて、error 行が 2 行以上出る入力で順を判定できる BDD シナリオを 1 つ追加する。

### 完了条件

- error 行が 2 行以上出る `--feature-flag` の入力について、標準エラーの行の順が CLI 契約から 1 つに決まる
- その順を判定する BDD シナリオが UC「feature flag を設定する」にある
- 「どの入力・状態の組み合わせでも標準エラーの行数と内容を 1 つに決める」が `--feature-flag` でも成り立つ

## CR-fd678b04-003: mode の値が列挙外・欠落のとき、その slot の従属キーを検査するかどうかを定める

- severity: spec-gap
- related_ids: [SPEC-001-01, SPEC-005-04, REQ-001]
- related_files: [docs/specs/latest/適用構成業務/適用構成定義フロー/feature flag を設定する/tier-facade.md, docs/specs/latest/適用構成業務/適用構成定義フロー/feature flag を設定する/spec.md, docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml]

### 観測した事実

`validate-config.sh --feature-flag` の実装は、mode の値が列挙外(例: `BLUE_MODE=parallel`)または欠落・空のときも、その slot を「off でない」として扱う。mode 自体の error 行に加えて、次の検査を行う。

- その slot の実装版・runner の必須検査
- 対応ジョブマップの検査
- runner への `--help` の問い合わせ

`RAPID_CROSSCHECK_MODE` が列挙外のときの速報 runner / worker の検査も同じ扱いである。この挙動は 2026-09 の完了時点から変えていない。

### 現在の仕様と問題

- tier-facade.md のキー表は、従属キーを「`<SLOT>_MODE≠off` のとき必須」と書く。mode 自体が列挙外・欠落のときに「off でない」とみなすかどうかは書いていない
- spec.md のシナリオ「違反は全件まとめて報告される」は「両方が出る」ことだけを求めるため、検査する実装も検査しない実装も通る
- 検査するかどうかで、同じ入力に対する error 行の件数と、runner への問い合わせの有無(最大で 1 slot あたり 4.6 秒の待ち)が変わる

元の方針資料には、列挙外の mode の扱いの記載が無い。どちらの案も元の方針と食い違わない。

### 変更してほしいこと

mode の値が列挙外・欠落・空のときの従属キーの扱いを、tier-facade.md のキー表(または CLI 契約の feature-flag.env の `validation_rules`)に 1 文で定める。選択肢は次のとおり。推奨は案 A。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A(推奨) | 現行どおり検査する(列挙外・欠落・空の mode は「off でない」として扱う) | 「違反は全件まとめて報告する」という共通の方針に合う。mode を直した後に出るはずの error を 1 回で直せる。実装とテストが変わらない | mode の書き間違いだけのときも、従属キーの error 行と runner への問い合わせが出る |
| B | 検査しない(mode の error 行だけを出し、その slot の従属キーの検査と runner への問い合わせを行わない) | 原因(mode の書き間違い)だけが出る | 実装の変更が要る。mode を直した後に、従属キーの error が初めて出る |

あわせて、列挙外の mode と従属キーの欠落が同時にある入力で、定めた扱いを判定できる BDD シナリオを 1 つ追加する。

### 完了条件

- mode が列挙外・欠落・空で、その slot の実装版または runner が無い入力について、error 行の件数と runner への問い合わせの有無が仕様から 1 つに決まる
- その扱いを判定する BDD シナリオが UC「feature flag を設定する」にある

## CR-fd678b04-004: 9 キー以外のキーの値を、検証器のプロセスの変数へ取り込まないことを定める

- severity: spec-gap
- related_ids: [SPEC-001-01, REQ-001]
- related_files: [docs/specs/latest/適用構成業務/適用構成定義フロー/feature flag を設定する/tier-facade.md, docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml]

### 観測した事実

`validate-config.sh --feature-flag` の実装は、feature-flag.env から変数として取り込むのを 9 キーだけにしている。9 キー以外のキー(例: `PATH`)は、キー名だけを一覧に記録し、値をプロセスの変数に載せない。

独立した検証で、`PATH=/invalid` と、コマンド置換の形(`$(touch ...)`)をキー・値に置いた設定を検証した。コマンド置換は実行されず、未知キーの warn と規定の検証結果だけが出た。独立した検証は、これを仕様に定めが無い安全側の判断として記録した(回答が要る前提)。

### 現在の仕様と問題

- tier-facade.md の設定契約は、feature flag が所有するのは 9 キーだけで、ファイルを `source` しないと書く。CLI 契約の `config_input_rules.env_files` は、キーと値の取り出し方を定める
- 9 キー以外のキーの値を、どこまで保持してよいか(プロセスの変数・環境変数へ載せてよいか)は書かれていない
- 定めが無いため、別の読み手(実行時に同じ設定を読む処理)が未知キーの値を変数・環境変数へ取り込む実装をしても、仕様には反しない。その場合、設定ファイルで `PATH` などのプロセスの環境を書き換えられる

元の方針資料の設定契約は 9 キーだけを示し、未知キーの扱いの記載は無い。この要求は「feature flag が持つのは 9 キーだけ」という元の方針と食い違わない。

### 変更してほしいこと

次のどちらにするかを決める。推奨は案 A。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A(推奨) | 仕様に書く。「feature-flag.env から値を取り込むのは 9 キーだけ。9 キー以外のキーは、値をプロセスの変数・環境変数へ取り込まない(キー名を warn・error の表示に使うだけ)」を、設定契約または `config_input_rules.env_files` に定める | 設定ファイルでプロセスの環境を書き換えられないことが、検証コマンド以外の読み手にも及ぶ。実装が変わらない | 仕様の記載が 1 文増える |
| B | 仕様に書かない(実装の判断のままにする) | 仕様の変更が要らない | 読み手ごとに扱いが分かれる余地が残る |

### 完了条件

- 9 キー以外のキーの値を変数・環境変数へ取り込むかどうかが、仕様から 1 つに決まる
- 案 A の場合、feature-flag.env を読むすべての処理(検証コマンドと実行時の読み手)に同じ規則が及ぶことが読み取れる
