# 実装からの変更要求

## CR-eff24f55-001: 設定ファイル検証が守る範囲(異常な入力・異常な環境)が未定義

- severity: blocker
- related_ids: [SPEC-004-04, REQ-004]
- related_files: [docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/tier-facade.md, docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml]

### 観測した事実

- `validate-config.sh --job-map` の独立検証で、4 回続けて新しい重大な指摘が出た。
- 4 回とも、異常な入力または異常な環境に対する堅牢性の指摘だった。
- 4 回の指摘は、いずれも実装で対応済みである。

| 回 | 指摘 | 実装の対応 |
|---|---|---|
| 1 | fixed_params の JSON 文字列内の未エスケープ制御文字(タブ・CR・ESC)を受理した | 拒否する |
| 2 | CSV 内の NUL バイトが読み込み時に消え、不正な値を受理した | 既存の文言で拒否する |
| 3 | 値とパスの制御文字をそのまま出力した。補助コマンドの失敗を検知しなかった。UTF-8 として不正なバイト列を受理した | 可視表記へ置き換える。終了コード 6 で終える。既存の文言で拒否する |
| 4 | 検証中にファイルが差し替わると、不正な行を受理した | 検証開始時の単一スナップショットだけを検証する |

- 4 回目の指摘の再現手順は次のとおり。
  - 旧ファイルのデータ行は `J1,/old,/s,[],60` である。
  - 新ファイルのデータ行は job_id に NUL バイトを含む `J<NUL>2,/new,/s,[],60` である。
  - 両ファイルとも、ヘッダーを含めて 2 行である。
  - 検証コマンドの事前のバイト点検の直後に、新ファイルを `mv` で旧ファイルのパスへ置き換える。
  - 結果は終了コード 0、`rows=1`、`job_id=J2 work_dir=/new` の受理だった。
  - この行は、旧ファイルにも新ファイルにも存在しない。
  - 新ファイルを単独で検証すると、終了コード 2 で拒否される。
- 当時の実装は、バイト点検と CSV 読み込みで同じパスを 2 回開いていた。
- CLI 契約の設定ファイル編集規則は「一時ファイルへ書いて `mv` で置き換える」である。検証中の置き換えは、この規則どおりの運用で起こり得る。
- 現在の実装は、4 回目の指摘に次の判断で対応している。

| 論点 | 実装済みの判断 |
|---|---|
| 検証の対象 | 検証開始時に入力を一時ファイルへ 1 回だけ複製する。点検と解析は複製だけを読む(単一スナップショット) |
| 検証中の差し替え | 複製した時点の内容だけで検証する。差し替えを検知も報告もしない |
| 一時ファイルの置き場所 | 環境変数 TMPDIR のディレクトリ。未設定なら `/tmp` |
| 一時ファイルの権限 | 所有者だけが読み書きできる(0600) |
| 一時ファイルの削除 | 読み込みを終えたら、成功でも失敗でも削除する |
| シグナル受信時 | HUP / INT / TERM を受けたら、複製を削除して終了コード 129 / 130 / 143 で終える。SIGKILL では複製が残り得る |
| 複製の失敗 | 検証 OK も検証違反も返さず、終了コード 6 で終える(文言は CR-eff24f55-002) |
| 出力するパス | 利用者が指定したパスを出す。一時ファイルのパスは出さない |

- 4 回目の再現手順を修正後に再実行すると、旧ファイルの内容(`job_id=J1 work_dir=/old`)だけで検証した。終了コードは 0 だった。
- 差し替えのタイミングを 5 か所に変え、正常な内容と不正な内容の両方向で計 10 ケースを確かめた。どのケースも、複製した時点の内容だけで判定した。
- 一時ファイルの複製には、ジョブマップの内容(credential_ref の参照名を含む)がそのまま入る。
- 一時ファイルを置くディレクトリに書き込めない環境では、正しいジョブマップでも終了コード 6 になる。
- 利用者は 3 回目の後に次の方針を決めた。
  - 仕様に無い壊れた入力は、既存のエラー文言で拒否する。
  - 同じ種類の新しい穴がまた出たら、実装を直さずに仕様の確定を待つ。
- 利用者は 4 回目の後、例外として検証中の差し替えだけを直すと決めた。
  - 修正後の独立検証は、差し替えの指摘が直ったかの確認だけに絞った。
  - 異常な入力・異常な環境の新しい穴の探索は、行っていない。

### 現在の仕様と問題

- 設定契約が定める入力形式は次のとおり。
  - CSV、1 行目はヘッダー、行頭 `#` の行と空行は無視する。
  - 改行コードは LF、文字コードは UTF-8 である。
  - セルは bash 単独で解析する。
- 次の論点は、仕様に定めが無い。

| 分類 | 定めが無い論点 |
|---|---|
| バイト | NUL バイト、UTF-8 として不正なバイト列、BOM、CR と CRLF 改行 |
| 行 | 最終行の改行なし、空白だけの行、行とセルの長さの上限、ヘッダーだけでデータ行が 0 件のファイル |
| 構造 | ヘッダー列名の重複、文字コードが不正なコメント行 |
| 環境 | 検証中のファイルの差し替え、検証に使う補助コマンドの失敗 |

- 守る範囲が決まっていない。そのため、実装と独立検証が異常系を 1 つずつ見つけ続け、4 回続けて検証が収束しなかった。
- 4 回目の対応(単一スナップショット、一時ファイルの扱い)は、仕様に根拠の無い実装の判断である。
  - 仕様が別の保証を選ぶと、実装の変更が必要になる。
- 守備範囲が決まるまで、この機能の異常系の検証は完了と判定できない。
- 同じ論点は、設定ファイルを読む他の機能(feature flag、クロスチェックのジョブマップ、対象カタログ)にもある。
  - 守備範囲が無いまま他の機能を実装すると、同じように検証が収束しない。
- 元の方針資料との照合結果は次のとおり。
  - 方針資料には、設定ファイルの文字コード・バイト異常・検証中の差し替えの記載が無い(新規の決定が必要)。
  - 方針資料には、検証器が入力を一時ファイルへ複製すること、その置き場所・権限・削除時期の記載が無い(新規の決定が必要)。
  - 方針資料の入力検証は、ジョブスケジューラから受け取る JOB_ID と PARAM の検証だけである。
  - 方針資料のジョブマップ CSV 例は、非 ASCII 文字の値を含む。
  - 方針資料は、fixed_params の要素に含まれる空白とカンマの維持を求める。
  - 方針資料は、リランでは最新のマップを再解決せず、元の解決結果を使うと定める。

### 変更してほしいこと

1. 設定ファイルを読む機能に共通する「入力の守備範囲」を、機能横断の規約として定める。
2. 守備範囲では、上表の論点ごとに扱いを 1 つに決める。
   - 拒否する(検証エラー)
   - 警告して受理する
   - 値の一部として受理する
   - 守備範囲の対象外とする(対象外なら、その旨を明記する)
3. 検証中のファイルの差し替えについて、検証コマンドが保証する内容を定める。
   - 推奨: 検証結果は、ある 1 時点のファイル内容(単一のスナップショット)だけに基づく。
   - 旧内容と新内容を混ぜた結果を返さない。
   - 実装は単一スナップショットを採用済みである。仕様で確定するか、別の保証へ変更する。
   - 単一スナップショットを一時ファイルで実現する場合は、次を定める。
     - 置き場所(実装は TMPDIR、未設定なら `/tmp`)
     - 権限(実装は所有者だけが読み書きできる 0600)
     - 削除の時期(実装は成功・失敗・HUP / INT / TERM の受信時に削除)
     - 置き場所に書き込めない環境の扱い(実装は終了コード 6)
4. 検証に使う補助コマンドの失敗を、守備範囲に含めるかを定める。
   - 含めるなら、失敗時に検証 OK も検証違反も返さないことを明記する。
   - 入力の複製の失敗も、同じ扱いに含めるかを定める。
5. 守備範囲に入れない異常環境(例: 意図的な関数の差し替え)を、対象外として明記する。
6. 方針資料の CSV 例(非 ASCII 文字、空白とカンマを含む固定引数)が、守備範囲の定めで受理されることを保つ。

### 完了条件

- 上表の全論点について、扱いが仕様に 1 つずつ書かれている。
- 検証中の差し替えに対する保証が、仕様に書かれている。
- 検証器が入力を一時ファイルへ複製する場合、その置き場所・権限・削除の時期が仕様に書かれている。
- 各論点に、実装が推測なしに書ける BDD シナリオまたは受け入れ基準がある。
- 設定ファイルを読む他の機能の仕様が、同じ守備範囲を参照している。
- 方針資料の CSV 例が、守備範囲の定めのもとで検証 OK になる。

## CR-eff24f55-002: 異常な入力の拒否と検証器の内部障害に、専用の error 行が無い

- severity: spec-gap
- related_ids: [SPEC-004-04]
- related_files: [docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml, docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/tier-facade.md]

### 観測した事実

- 利用者の方針により、実装は既存の文言を流用して拒否している。

| 異常 | 現在の出力 | 終了コード |
|---|---|---|
| NUL バイトを含む行 | `error: csv quote is invalid line=N path: <path>` | 2 |
| UTF-8 として不正なバイト列を含む行(コメント行を含む) | `error: csv quote is invalid line=N path: <path>` | 2 |
| バイト点検の補助コマンドの失敗 | `error: internal command failed commands=tr,sed path: <path>` | 6 |
| 入力の複製の失敗(一時ファイルを作れない、複製が途中で失敗した) | `error: internal command failed commands=tr,sed path: <path>` | 6 |
| job_id 重複検査の補助コマンドの失敗 | `error: internal command failed commands=sort` | 6 |

- 文字コード違反の拒否は、文言から原因(文字コード)を読み取れない。
- 例: 別の文字コードのコメント行を含むファイルでは、利用者は引用符の誤りを探して迷う。
- `internal command failed` の行は、CLI 契約に無い文言である。
- 入力の複製の失敗は、新しい文言を作らず、バイト点検の失敗と同じ行で報告している。
  - `commands=` には、実際に失敗した処理(一時ファイルの作成・複製)ではなく、点検の補助コマンド名が出る。
  - 利用者は、一時ファイルの置き場所の問題を、点検の補助コマンドの問題と読み違え得る。
- どの内部障害でも、stdout は出していない。

### 現在の仕様と問題

- CLI 契約の `validate-config.sh` の stderr には、文字コード違反と NUL バイトの error 行が無い。
- CLI 契約の `validate-config.sh` の終了コード 6 の条件は「runner の `--help` 問い合わせの準備失敗」だけである。
- 共通の終了コード表は、6 を「実行エラー(内部エラーを含む)」と定める。
- 検証器の内部障害で 6 を返すことは、共通表とは整合するが、コマンド別の条件に無い。
- 入力の複製の失敗の終了コードと error 行も、仕様に定めが無い。
- 方針資料には、設定検証の error 文言の記載が無い(新規の決定が必要)。

### 変更してほしいこと

1. 入力の守備範囲(CR-eff24f55-001)で拒否すると決めた異常ごとに、原因が文言から分かる error 行を CLI 契約に定める。
   - 例: 文字コード違反と NUL バイトを、引用符の誤りと別の文言にする。
   - 行番号とパスの表記は、既存の error 行の書式に合わせる。
2. 文字コード違反の検査に、コメント行を含めるかを明記する。
3. 検証器の内部障害(補助コマンドの失敗など)を守備範囲に含める場合は、次を定める。
   - `validate-config.sh` の終了コード 6 の条件に、検証器の内部障害を加える。
   - 内部障害の error 行の文言を定める。
   - 入力の複製の失敗を、内部障害に含めるかを定める。含めるなら、その error 行の文言を定める。
   - 内部障害のとき stdout を出すかを定める。

### 完了条件

- 拒否する異常ごとに、error 行の文言と終了コードが CLI 契約にある。
- 利用者が、error 行だけで文字コード違反と引用符の誤りを区別できる。
- `validate-config.sh` の終了コード 6 の条件に、検証器の内部障害の扱いが書かれている(対象外と決めた場合は、その旨が書かれている)。
- 入力の複製の失敗について、error 行と終了コードが CLI 契約にある(内部障害に含めない場合は、その旨が書かれている)。

## CR-eff24f55-003: 任意入力を出力するときの制御文字の表記が未定義

- severity: spec-gap
- related_ids: [SPEC-004-04, SPEC-001-01]
- related_files: [docs/specs/latest/_cross-cutting/ux-ui/ui-design.md, docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml]

### 観測した事実

- 3 回目の独立検証で、次の出力が確認された。
  - セルの値に含まれる ESC シーケンスが、stdout にそのまま出た。
  - 改行を含むファイル名を渡すと、stdout の行数が 3 行から 4 行に増えた。
- 実装は、任意入力(セルの値、列名、パス、引数)を出力するとき、次の表記へ置き換えている。

| 対象 | 表記 |
|---|---|
| 改行 | `\n` |
| タブ | `\t` |
| その他の U+0001〜U+001F と U+007F | `\u00XX`(16 進小文字 4 桁) |
| UTF-8 で符号化した U+0080〜U+009F | `\u0080`〜`\u009f` |

- 実装は、バックスラッシュを置き換えていない。
  - 利点: 制御文字を含まない値の出力は、1 バイトも変わらない。
  - 欠点: 生のタブと、2 文字の `\t` を表示上区別できない。
- 実装は、パスに含まれる UTF-8 として不正なバイト(制御文字以外)を置き換えていない。
- 先行機能「feature flag を設定する」の stderr は、値・キー名・パスをそのまま出力している。
  - 例: `error: invalid value key=... value=...`、`warn: unknown key key=...`

### 現在の仕様と問題

- 出力フォーマット規約は、次の 2 点を定める。
  - ANSI エスケープを出さない。
  - 1 行 1 事実とする。
- 任意入力に制御文字が含まれるときの置き換え表記は、定めが無い。
- 規約を守る方法が機能ごとに異なり得る。実際に、先行機能の stderr には同じ穴が残っている。
- 方針資料には、出力の制御文字の扱いの記載が無い(新規の決定が必要)。
- 方針資料のジョブマップ例は、ドライブ文字とバックスラッシュを含むパスを使う。
  - バックスラッシュを置き換える表記にすると、このパスの表示が変わる。

### 変更してほしいこと

1. 任意入力を stdout / stderr に出すときの制御文字の表記規則を、出力フォーマット規約に定める。
2. 規則には次を含める。
   - 置き換える文字の範囲(C0 制御文字、DEL、C1 制御文字)
   - 置き換え後の表記
   - バックスラッシュを置き換えるか(方針資料のパス例の表示への影響を考慮する)
   - UTF-8 として不正なバイトを含む引数(パスなど)の表記
   - 置き換え前と置き換え後のどちらの値で、`key=value` と `key: value` を選ぶか
3. `--verbose` の fixed_params の JSON 表記と、この表記規則の関係を定める。
4. この規則を、既存の全コマンドの stdout / stderr に適用する。先行機能「feature flag を設定する」の stderr を含める。

### 完了条件

- 出力フォーマット規約に、制御文字の表記規則がある。
- 制御文字を含む値を出力するシナリオが、機能横断で 1 つ以上ある。
- 「feature flag を設定する」の stderr の仕様が、同じ表記規則を参照している。
- 方針資料のパス例の表示が、規則の適用後にどうなるかが仕様から読み取れる。

## CR-eff24f55-004: 実装の実行前提(bash の版、ジョブマップの想定最大行数)が実装向けの仕様に無い

- severity: spec-gap
- related_ids: [SPEC-004-04, B.2.1.1]
- related_files: [docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/tier-facade.md, docs/nfr/latest/nfr-grade.yaml]

### 観測した事実

- 実装は、bash の版に依存しない構文を選んだ。対象の版が分からなかったためである。
  - 例: job_id の重複検査で、連想配列を使わず外部コマンドの並べ替えを使った。
- 独立検証は、ジョブマップの行数を増やして処理時間を測った。
  - 1 回目: 重複検査が全組合せ比較で、2000 行で約 14 秒だった。
  - 4 回目: map_version が全行異なるとき、4000 行で約 23 秒だった。
- 独立検証は、想定最大行数が未定義のため、性能の指摘を重大と判定できなかった。
- インフラ設計の成果物には「bash 5」の記載がある。

### 現在の仕様と問題

- 実装規約、UC 仕様、実装設定のどれにも、対象の bash の版の定めが無い。
- 非機能要求は CLI の応答時間の目標(10 秒)を定める。
- ジョブマップの想定最大行数は定めが無い。そのため、性能目標を満たすかを判定できない。
- 方針資料は、実装言語をシェルスクリプトとする。bash の版とジョブマップの規模の記載は無い(新規の決定が必要)。

### 変更してほしいこと

1. 実装が前提にしてよい bash の最低版を、実装向けの仕様または規約に明記する。
2. インフラ設計の「bash 5」と、同じ値にそろえる。
3. 1 つのジョブマップの想定最大行数を定める。
