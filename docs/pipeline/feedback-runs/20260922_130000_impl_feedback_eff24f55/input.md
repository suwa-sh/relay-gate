# 実装からの変更要求

## CR-eff24f55-006: 重複した job_id の報告で列挙する行番号が、仕様本文と BDD で食い違う

- severity: spec-gap
- related_ids: [SPEC-004-04, REQ-004]
- related_files: [docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml, docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/tier-facade.md, docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/spec.md]

### 観測した事実

- `validate-config.sh --job-map` は、同じ job_id が複数行にあると `error: duplicate job_id job_id=<v> lines=<n1,n2,...>` を出して終了コード 2 で終える。
- `lines=` に列挙する行番号の定めが、仕様の中で 2 通りある。

| 出所 | 記載 | 2 行目と 5 行目に JOB001 がある入力の期待値 |
|---|---|---|
| CLI 契約の `validate-config.sh` の stderr | 2 回目以降の行番号をカンマ区切りで全部 | `lines=5` |
| tier 仕様の列検証表(job_id の行) | 2 回目以降の行番号をカンマ区切りで全部 | `lines=5` |
| UC 仕様の E2E 完了条件の BDD | `lines=2,5` | `lines=2,5`(初出行を含む) |
| tier 仕様のティア完了条件の BDD | `lines=2,5` | `lines=2,5`(初出行を含む) |

- tier の feature ファイルは、tier 仕様の BDD と同じ文言である。
- 実装は BDD に合わせ、その job_id が現れた行番号を出現順に全部並べる。独立検証の実測では、2・3・4 行目に同じ job_id がある入力で `lines=2,3,4` になった。
- 仕様本文に合わせると tier の BDD が fail する。BDD に合わせると仕様本文と食い違う。両方を同時に満たす実装は無い。
- 独立検証は 2 回続けて、この食い違いを major として指摘した。仕様の中の矛盾のため、実装の blocker にはしていない。
- 対象カタログの重複を報告する `error: duplicate target ... lines=<n1,n2,...>` も、CLI 契約で同じ注記(2 回目以降の行番号)を持つ。

### 現在の仕様と問題

- 本文と BDD のどちらが正か、仕様から決められない。
- 実装者と検証者が別の出所を読むと、別の答えになる。今回の実装は BDD を優先した。
- 対象カタログの検証(別の UC)も同じ注記に従うため、同じ食い違いが再び起こり得る。
- 元の方針資料との照合結果: 方針資料はジョブマップを「1 行 1 job_id」と定めるが、重複したときの報告形式の記載は無い。どちらに統一しても方針資料と矛盾しない。

### 変更してほしいこと

1. `lines=` に「初出行を含める」か「2 回目以降だけ」かを 1 つに決め、仕様本文 2 か所と BDD 2 か所を同じ内容にする。
2. 推奨は「初出行を含める(その job_id が現れた行番号を出現順に全部)」である。
   - 利用者は、重複した全行を 1 行の error で把握できる。
   - BDD と現在の実装に一致し、実装の変更が要らない。
3. 「2 回目以降だけ」に統一する場合は、BDD の期待値を `lines=5` に変える。
4. 対象カタログの重複を報告する error 行の注記も、同じ規則にそろえる。

### 完了条件

- 仕様本文と BDD で、`lines=` に列挙する行番号の規則が一致している。
- 2 行目と 5 行目に同じ job_id がある入力に対する期待出力が、仕様本文だけから一意に決まる。
- 対象カタログの重複を報告する error 行の注記が、同じ規則になっている。

## CR-eff24f55-007: credential_ref が参照名の形に合わず、パスにも秘密にも見えない値の扱いが未指定

- severity: spec-gap
- related_ids: [SPEC-004-04, REQ-004]
- related_files: [docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/tier-facade.md, docs/specs/latest/適用構成業務/適用構成定義フロー/slot ごとのジョブマップを定義する/spec.md, docs/specs/latest/_cross-cutting/api/cli-command-contract.yaml]

### 観測した事実

- 仕様は credential_ref を参照名 `^[A-Za-z0-9_.-]*$`(空も可)と定める。
- `/` を含む値と `BEGIN` を含む値は `warn: credential_ref looks like a secret or path line=N job_id=<v>` で報告し、拒否しない。UC 仕様の業務ルールは、この扱いに「仮採用」と注記している。
- 正規表現に合わず、`/` も `BEGIN` も含まない値(例: 空白・記号・非 ASCII 文字を含む値)の扱いは、warn か error か、どの文言か、のどれも仕様に無い。
- CLI 契約の `validate-config.sh` の stderr に、credential_ref の error 行は無い。
- 実装は「同じ warn を出して受理する。値は診断に出さない」を選んだ。
- この判断は、2026-09-19 のレビューで利用者が実装の前提として承認した。
- 独立検証は、仕様に定めが無いため、2 回続けて major(秘密情報に関わる境界)として確認を求めた。仕様が変わらない限り、次回以降の検証でも同じ指摘が出る。

### 現在の仕様と問題

- 参照名の形式(正規表現)は定義されているが、形式に合わない値の扱いは `/` と `BEGIN` の 2 パターンだけが定義されている。
- 残りの形式違反は、秘密情報の混入を見逃すか、参照名として解決できない値を受理するかの境界である。実装で決める事項ではない。
- 「仮採用」の注記が残っているため、実装者と検証者は毎回この扱いを確認対象にする。
- 元の方針資料との照合結果: 方針資料は「認証情報そのものは保存せず、認証情報の参照名だけを保存する」と定める。参照名の形式と、形式に合わない値の扱いの記載は無い(新規の決定が必要)。warn でも error でも方針資料と矛盾しない。

### 変更してほしいこと

1. 列検証表に「正規表現に合わない値(`/` も `BEGIN` も含まない)」の行を追加し、扱いを 1 つに決める。
   - 案 A(現在の実装。レビューで承認済み): 同じ warn を出して受理する。参照名の形式が認証情報ストアの運用に依存するため実装側で確定しない、という理由を契約に書く。
   - 案 B: `error: credential_ref is invalid line=N job_id=<v>` で拒否し、終了コード 2 とする。CLI 契約の stderr に追加する。
2. どちらの案でも、credential_ref の値を診断行に出さない規則を明記する(現在は文言の例に値が無いだけで、規則としては書かれていない)。
3. UC 仕様の「仮採用」の注記を、確定した内容に置き換える。

### 完了条件

- 参照名の形式に合わないすべての値について、warn か error かと、その文言が仕様から一意に読める。
- credential_ref の値を診断行に出さない規則が仕様に書かれている。
- UC 仕様の「仮採用」の注記が消えている。
