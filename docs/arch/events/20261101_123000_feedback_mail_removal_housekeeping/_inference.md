## 推論(CR-e4ea8aaa-002 ハウスキープ新設)

- 配置(tier-ops): 実装 tier は bootstrap で 4 つに確定し、管理 DB の所有ティアは tier-ops。housekeep はジョブスケジューラの定期ジョブとして facade から分離され、成果物ルートと管理 DB を走査する運用スクリプトで hang-detector と同じ形。新しい tier を作ると契約・uc-map への波及が大きい
- BC(新設): RDRA が独立業務とし(利用者確定)、方針資料も C1 で独立要素にしている。行の削除は BC-004 の不変条件(監視は通知のみ・中止は状態更新のみ)と相容れない。BC-006 は永続エンティティを持たず、ハウスキープ設定は他の設定と同じく BC-005 が所有する。サブドメインは保守機能として generic
- 削除の所有: SR-003 / SR-004 は作成・更新の所有だけを定めていたため、削除の例外を CTR-008 で一意に定めた。専用 DB ロール(SELECT と DELETE だけ)と業務用ロールに DELETE を足さない規則は条件と方針資料のとおり
- イミュータブルデータモデル(arch-decision-007)との関係: 保持期間内の追記・状態遷移のイミュータブル性は保ち、保持期間後の物理削除はハウスキープの削除単位でだけ行う例外とした
- 仕様で確定するもの(arch では決めない): ハウスキープ設定のファイル名・キー名、削除待ちの置き場の場所、失敗後に残りの単位を続けるか、終了コードの値
